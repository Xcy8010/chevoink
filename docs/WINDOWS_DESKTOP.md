### 剩余工作的执行顺序

1. 确定获批签名渠道/发布者与受保护的 updater 密钥配置；不在聊天、仓库或日志传私钥。签名渠道未定前，不编造可运行的供应商签名流水线。
2. 配置同一构建 SHA 的受保护签名发布作业：签应用与安装器、可信时间戳，再签最终 updater 产物；生成摘要及 SBOM。新正式构建使用未占用版本，不覆盖现有候选包。
3. 补真实 WebView2 E2E、坏签名/下载中断/安装失败演练，以及下方 Win10、DPI、性能、安全与卸载验证；用户已确认的五项不再重复标成“未测”。
4. 从 Release 草稿回下载两种安装包，运行 `desktop/windows/verify-installer.ps1`，再独立验证 updater 签名和安装/更新。脚本只检查文件名、内嵌产品版本、可信摘要、预期发布者的有效 Authenticode 与时间戳，不代替嵌入应用签名验证或完整发布批准。
5. 全部门槛通过后公开独立 Windows Release（`latest=false`），同步同摘要官网镜像，最后发布稳定清单并验证设置下载入口。只发布壳和下载资产不重启业务 API。

脚本示例（变量必须来自已批准签名身份和可信构建记录，不从待验文件自行推导期望值）：

```powershell
./desktop/windows/verify-installer.ps1 -Installer $installerPath -Version $releaseVersion -ExpectedSha256 $trustedSha256 -ExpectedSignerThumbprint $approvedThumbprint
```

### 依赖审计限定结论

`237abf2` 的 RustSec JSON 报告中 `vulnerabilities.count` 为 0，但仍有维护性和健全性警告，不可宣称零风险：

- Windows 目标包含 `unic-char-property`、`unic-char-range`、`unic-common`、`unic-ucd-ident`、`unic-ucd-version` 五个停止维护的间接依赖，经 `urlpattern` → `tauri-utils` 引入。当前未以忽略规则消除警告；后续升级 Tauri 时必须复核锁文件及导航、权限匹配回归，正式发布前再次扫描并评估。
- `proc-macro-error` 的停止维护警告及 `glib` 的 `RUSTSEC-2024-0429` 健全性警告出现在跨平台锁文件，但不在本次 Windows 目标依赖图中。这一范围判断不适用于未来 Linux 构建。
- CI 保存原始 `rust-audit.json` 与 Windows 依赖声明清单；审计数据库会变化，当前通过不能替代正式发布提交的重跑，也不能替代宿主攻击测试和许可证审查。

## 运维原则

官网域名和 appId 不随版本变化；更新不清 Cookie、草稿、任务布局或审查。只更新壳时不重启生产 API。网页兼容改动需正常主线 CI/部署，生产任务中断需要该次有效授权。

正式资产按版本不可覆盖，保留当前和前一稳定版本及对应签名/摘要。故障优先停止扩大分发，再用更高版本的已知良好代码前滚恢复，不关闭版本或签名校验强制降级。

发布事故、密钥轮换、WebView2/Tauri 安全更新及隐私行为变化均需复验并更新本文；不将候选实现自动改写为已支持。
