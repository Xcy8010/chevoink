# 18. Agent 任务 Token 预算与死循环防护优化方案

> 状态：调查结论 + 待确认优化计划（本文档为任务③交付，未落地任何代码）
> 调查时间：2026-09-02 · 基于当前 main（6e0f3c9）代码核验

## 一、现状盘点（代码核验）

### 1.1 预算体系

| 层级 | 轮次上限 | Token 预算 | 备注 |
|---|---|---|---|
| 主 run | `AGENT_MAX_TURNS` 默认 **100** | `AGENT_RUN_TOKEN_BUDGET` 默认 **200 万** | 请求参数 `tokenBudget` 只能下调（`min(env, params)`），不能上调 |
| 上下文窗口 | — | `AGENT_CONTEXT_WINDOW_TOKENS` 默认 **128k** | 65% 注入提醒、78% 自动压缩（防溢窗） |
| 子 Agent | `min(env, 24)` 轮 | 硬钳 **16k**（`SUBAGENT_TOKEN_CEILING`，不暴露配置） | 全局并发 8；超限强制无工具总结收尾 |
| wrap-up | 预算/轮次耗尽后 1 次 | 计入用量 | 无工具总结；待办未完→failed 可「继续执行」续跑 |
| 并发闸 | — | — | 同会话仅 1 个 run；单用户并发 `AGENT_USER_MAX_CONCURRENT` 默认 2 |

### 1.2 现有防死循环 / 兜底机制

1. **轮次 + 预算双上限**：任一耗尽 → 注入「立即停止调用工具」强指令 → wrap-up 总结 → 终态
2. **todo 回填拦截**：待办未完就想结束最多拦截 4 次（防早停，同时限制该路径死循环）
3. **结构熔断**：卷章结构工具（chapter_create/move 等）连续失败 3 次 → 硬熔断停止写入
4. **ask_user 提问预算**：每任务最多 3 次，用尽返回提示让模型自行决策
5. **无效工具协议安全停止**：模型输出解析失败不视为已执行，本轮安全终止
6. **子 Agent 三重钳**：轮次 24 + token 16k + 并发 8，超限强制总结
7. **Credits 实时结算**：每次模型调用即时扣费，成本由用户额度自担
8. **用户中止**：abort → paused，不产生继续消耗

### 1.3 缺口（对照主流 Agent Loop 工程实践）

| # | 缺口 | 风险场景 | 行业惯例 |
|---|---|---|---|
| G1 | **相同工具 + 相同参数连续重复调用检测** | 反复 search 同一词、反复 read 同一文件、chapter_move 同参数盲试——每轮都真实扣费 | 主流 loop 标准出口：连续 2~3 次相同签名即强制中断（唐巧《Agent Loop 简介》、deepseek-harness#3228 的反面教材均为佐证） |
| G2 | **正文 / 思考信道重复文本检测** | `text.delta` / `reasoning-delta` 中同一段话或同一句式反复输出；思考信道空转重复一个短语 | Claude Code 等在流聚合层做 n-gram 滑窗重复度检测；本项目只有**事后**质量审查（humanity-quality 的 image_repetition/sentence_homology，advisory 级），无运行时熔断 |
| G3 | **墙钟时长上限** | 用户离开后任务低速空转：每轮都有真实模型调用，慢速也持续烧 credits，200 万预算可能数小时才耗尽 | 常见做法：token 之外再加 wall-clock 上限作为第三道闸 |

## 二、预算是否偏少的判断

**结论：不偏少，重点应放在「防浪费」而非「扩预算」。**

- 单章全流程（大纲/草稿/修订/质量审查）实测量级约 15–30 万 token；连写六章 90–180 万，200 万主预算可覆盖
- DeepSeek 缓存命中后输入 token 按 0.1 折计价，实际成本进一步下降（缓存优化已在 48c322b 落地）
- 对比开源 AI 小说生成器（AI_NovelGenerator 等多为固定 pipeline，每步单次调用、无 agentic loop）：本项目是真正的自主 loop + 双上限 + 三层熔断，预算纪律已属第一梯队
- 子 Agent 16k 对「短平快研究」定位偏紧但合理；复杂任务应由主 Agent 自行执行或拆分多次调用，无需放宽
- Credits 制度下预算烧的是用户自己的额度：**死循环的真实代价是用户体验与信任，而非平台成本**——这正是 G1/G2 的价值所在

## 三、优化计划（待确认后落地，优先级排序）

### P0：重复工具调用熔断（收益最大、实现最小）
- 位置：`loop.ts` 工具执行处
- 机制：维护最近调用的签名（工具名 + 规范化参数 hash）滑窗
  - 连续 3 次同签名 → 不执行，直接返回提示性失败：「与上次调用完全相同，请更换参数或换一种方法」
  - 连续 4 次同签名 → 强制走 wrap-up 收尾（failed，可续跑）
- 边界：读类工具允许「再确认」一次（阈值 3 已留余量）；签名 hash 对大参数做截断归一化防内存膨胀

### P1：正文 / 思考信道重复检测
- 位置：`loop.ts` 流聚合处（text.delta / reasoning-delta 已有统一通道）
- 机制：滑动窗口（约 2000 字）内 50 字滑窗 n-gram 重复出现 ≥3 次 → 注入一次性系统提醒「检测到重复输出，请立即推进新内容」
  - 提醒后再次命中 → 终止 run（failed，原因=输出重复，可续跑）
  - 纯内存滑窗实现，O(n) 成本，不影响流式延迟
- 注：避免误伤「有意重复」（如小说里的歌词、咒语复现），阈值与窗口长度落地前需用真实章节回放校准

### P2：墙钟时长上限
- 新增 `AGENT_RUN_WALL_CLOCK_MINUTES`（默认建议 30）
- loop 每轮开始检查；超时走预算耗尽同款 wrap-up 路径
- 目的：封顶单 run 的最坏情况，防止低速空转长时间占用并发额度

### P3（可选，暂缓）：子 Agent 预算分级
- 研究/continuity 类 16k 维持；compile/audit 类可放宽 32k
- 等 P0–P2 上线观察后再议

### 明确不做
- ❌ 不上调 200 万主预算：够用且与 credits 定位一致
- ❌ 不新增全局并发闸：会话级 + 用户级（默认 2）+ 子 Agent 全局（8）三层已够
- ❌ 不做服务端语义级「任务是否在正常推进」判定：误杀率高，P0/P1 的确定性信号已足够

## 四、测试与验收

1. 单测：签名重复滑窗、n-gram 检测滑窗、wall-clock 超时路径、wrap-up 触发顺序（预算 < 轮次 < 熔断的优先级不回退）
2. 回归：todo 拦截 4 次、结构熔断 3 次、提问预算 3 次、子 Agent 16k 钳制全部保持
