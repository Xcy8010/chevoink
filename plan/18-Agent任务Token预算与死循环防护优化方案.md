# 18. Agent 任务 Token 预算与死循环防护优化方案

> 状态：调查结论 + 待确认优化计划（本文档为任务③交付，未落地任何代码）
> 调查时间：2026-09-02 · 基于当前 main（6e0f3c9）代码核验

## 一、现状盘点（代码核验）

### 1.1 预算体系

| 层级 | 轮次上限 | Token 预算 | 备注 |
|---|---|---|---|
| 主 run | `AGENT_MAX_TURNS` 默认 **100** | `AGENT_RUN_TOKEN_BUDGET` 默认 **200 万** | 请求参数 `tokenBudget` 只能下调（`min(env, params)`），不能上调 |
| 上下文窗口 | — | `AGENT_CONTEXT_WINDOW_TOKENS` 默认 **128k** | 65% 注入提醒、78% 自动压缩（防溢窗） |
| 子 Agent | `min(env, 24)` 轮 | 硬钳 **16k**（`SUBAGENT_TOKEN_CEILING`，不暴露配置） | 全局并发 8；超限强制无工具总结收尾 |
| wrap-up | 预算/轮次耗尽后 1 次 | 计入用量 | 无工具总结；待办未完→failed 可「继续执行」续跑 |
| 并发闸 | — | — | 同会话仅 1 个 run；单用户并发 `AGENT_USER_MAX_CONCURRENT` 默认 2 |

### 1.2 现有防死循环 / 兜底机制

1. **轮次 + 预算双上限**：任一耗尽 → 注入「立即停止调用工具」强指令 → wrap-up 总结 → 终态
2. **todo 回填拦截**：待办未完就想结束最多拦截 4 次（防早停，同时限制该路径死循环）
3. **结构熔断**：卷章结构工具（chapter_create/move 等）连续失败 3 次 → 硬熔断停止写入
4. **ask_user 提问预算**：每任务最多 3 次，用尽返回提示让模型自行决策
5. **无效工具协议安全停止**：模型输出解析失败不视为已执行，本轮安全终止
6. **子 Agent 三重钳**：轮次 24 + token 16k + 并发 8，超限强制总结
7. **Credits 实时结算**：每次模型调用即时扣费，成本由用户额度自担
8. **用户中止**：abort → paused，不产生继续消耗

### 1.3 缺口（对照主流 Agent Loop 工程实践）

| # | 缺口 | 风险场景 | 行业惯例 |
|---|---|---|---|
| G1 | **相同工具 + 相同参数连续重复调用检测** | 反复 search 同一词、反复 read 同一文件、chapter_move 同参数盲试——每轮都真实扣费 | 主流 loop 标准出口：连续 2~3 次相同签名即强制中断（唐巧《Agent Loop 简介》、deepseek-harness#3228 的反面教材均为佐证） |
| G2 | **正文 / 思考信道重复文本检测** | `text.delta` / `reasoning-delta` 中同一段话或同一句式反复输出；思考信道空转重复一个短语 | Claude Code 等在流聚合层做 n-gram 滑窗重复度检测；本项目只有**事后**质量审查（humanity-quality 的 image_repetition/sentence_homology，advisory 级），无运行时熔断 |
| G3 | **墙钟时长上限** | 用户离开后任务低速空转：每轮都有真实模型调用，慢速也持续烧 credits，200 万预算可能数小时才耗尽 | 常见做法：token 之外再加 wall-clock 上限作为第三道闸 |

## 二、预算是否偏少的判断

**结论：默认 200 万不偏少、不上调；但开放「显式上调」通道（硬顶 500 万），把选择权交给 credits 所有者。**

- 单章全流程（大纲/草稿/修订/质量审查）实测量级约 15–30 万 token；连写六章 90–180 万，200 万主预算可覆盖
- DeepSeek 缓存命中后输入 token 按 0.1 折计价，实际成本进一步下降（缓存优化已在 48c322b 落地）
- 对比开源 AI 小说生成器（AI_NovelGenerator 等多为固定 pipeline，每步单次调用、无 agentic loop）：本项目是真正的自主 loop + 双上限 + 三层熔断，预算纪律已属第一梯队
- 子 Agent 16k 对「短平快研究」定位偏紧但合理；复杂任务应由主 Agent 自行执行或拆分多次调用，无需放宽
- Credits 制度下预算烧的是用户自己的额度：**死循环的真实代价是用户体验与信任，而非平台成本**——这正是 G1/G2 的价值所在
- **预算与防死循环解耦**：P0–P2 落地后，死循环由确定性信号（重复签名/重复文本/墙钟）拦截，预算只是最后兜底——上调默认值不带来任何防死循环收益，只会推后失控 run 的 wrap-up 触发点、拉长单 run 最坏时长。故默认值不动
- **显式上调通道**：请求参数 `tokenBudget` 现状只能下调（`min(env, params)`，loop.ts L1006）；改为 `clamp(params, 500, HARD_CEILING=500万)`——作者可为长任务（连写七章以上）显式上调至硬顶内，服务端强制钳制硬顶防失控；前端后续可在任务设置暴露「长任务模式」开关（本期可只做 API 层）
- **长任务能力不靠上调默认预算，靠 P4 检查点自动续跑**：预算切片化（200 万/片 × ≤4 次续跑 = 链总 ≤500 万硬顶），单片纪律不变、链长按需伸展——兼得「单片防浪费」与「codex 式跑到完为止」

## 三、优化计划（待确认后落地，优先级排序）

> 对现有工作流的影响：P0–P2 全部是「新增出口条件」，不改动正常路径（定位→大纲→场景任务→草稿→审校→桥接→记忆）的流程、提示词与工具语义；唯一行为变化是原本「静默烧到预算耗尽」的失控 run 会提前带明确原因终止（failed 可续跑）。对产出质量中性偏正：减少浪费燃烧即减少「预算被空转吃掉、正事没做完就被 wrap-up」的概率。

### P0：重复工具调用熔断（收益最大、实现最小）
- 位置：`loop.ts` 工具执行处
- 机制：维护最近调用的签名（工具名 + 规范化参数 hash）滑窗
  - 连续 3 次同签名 → 不执行，直接返回提示性失败：「与上次调用完全相同，请更换参数或换一种方法」
  - 连续 4 次同签名 → 强制走 wrap-up 收尾（failed，可续跑）
- **重试排除（防误杀关键）**：签名滑窗**只记成功执行**的调用；同签名上一次为失败（网络抖动/5xx/审批超时等瞬态错误）时允许原样重试且不计入连续次数——否则模型对瞬态失败的合法重试会被当重复调用拦掉，把任务误杀在半路
- 边界：读类工具允许「再确认」一次（阈值 3 已留余量）；签名 hash 对大参数做截断归一化防内存膨胀
- 优先级：与既有结构熔断（STRUCTURE_MUTATION_TOOLS 连败 3 次硬停）重叠时结构熔断优先——它更具体、语义更硬（直接停写），P0 滑窗对其仅作补充计数

### P1：正文 / 思考信道重复检测（两阶段：先观察后干预）
- 位置：`loop.ts` 流聚合处（text.delta / reasoning-delta 已有统一通道）
- 机制：滑动窗口（约 2000 字）内 50 字滑窗 n-gram 重复出现 ≥3 次 → 注入一次性系统提醒「检测到重复输出，请立即推进新内容」
  - 提醒后再次命中 → 终止 run（failed，原因=输出重复，可续跑）
  - 纯内存滑窗实现，O(n) 成本，不影响流式延迟
- **阶段一（观察模式）**：上线初期只记命中日志与样本、零干预（不提醒不终止），收集一周真实命中样本确认误杀面；**阶段二（干预模式）**：样本确认安全后再开启提醒与终止，经 `isAgent2FeatureEnabled` 灰度名单放量
- 误杀面评估：50 字 n-gram 要求逐字相同，进展播报句（含章号/字数变量）与有意重复（歌词、咒语复现，通常 <50 字逐字段）均不易命中；观察模式兜底剩余不确定性

### P2：墙钟时长上限（总帽 + 空转帽双条件）
- 新增 `AGENT_RUN_WALL_CLOCK_MINUTES`（默认 **60**）与 `AGENT_RUN_IDLE_MINUTES`（默认 **10**）
- 总帽：单 run 墙钟超 60 分钟 → 走预算耗尽同款 wrap-up 路径（封顶最坏情况；默认 30 会误杀连写多章的合法长任务，实测单章全流程含审校可达 10–20 分钟）；**P4 长任务模式（自动续跑启用）下总帽默认 180 分钟**，env 可调
- 空转帽：连续 10 分钟**既无工具完成事件也无正文/思考增量** → 立即 wrap-up（精确命中「用户离开后低速空转」场景，比总帽更早止损）
- **等待排除（防误杀关键）**：`pendingApproval`（审批超时默认 10 分钟）与 `pendingQuestion`（等作者回答）挂起期间空转钟归零重计——否则等审批的合法等待会被空转帽误杀
- loop 每轮开始检查总帽；空转钟在流聚合与工具完成回调处刷新

### P3（可选，暂缓）：子 Agent 预算分级
- 研究/continuity 类 16k 维持；compile/audit 类可放宽 32k
- 等 P0–P2 上线观察后再议

### P4：检查点式自动续跑——codex 式长任务能力（核心新增）

> 目标：作者视角「任务跑到完为止」——连写十章、整卷重构这类数小时级任务不需要人守着点「继续执行」；同时不引入 codex 自己都没防住的 compaction 空转烧钱事故。

**codex/opencode/Claude Code 长任务机制核验结论**（codex-rs/core/src/compact.rs 源码 + openai/codex#31351 + arXiv:2604.14228 Claude Code 设计空间论文）：

| 机制 | codex 实现 | 本项目现状 | 差距 |
|---|---|---|---|
| 总预算出口 | **无**：token_usage 只累计展示/计费，不作终止条件；终止由「模型返回纯文本=任务完成」驱动 | 200 万硬出口（wrap-up 终止） | 长任务真天花板在此，不在窗口 |
| 上下文续命 | run 内自动 compaction：接近窗口时总结→替换历史→重注入 initial context/world_state→**继续跑**，用户无感 | 78% 自动压缩已有 ✓，但压缩后仍受总预算约束 | 压缩与预算解耦 |
| 轮次上限 | max_turns 为 headless 治理**可选项**，非默认出口 | 100 轮硬帽 | 续跑模式下需切片 |
| 进度外部化 | 文件系统/git 是外部记忆，context 只留摘要 | 章节/记忆/todo/基线全在 DB——**比 codex 更强** | 无 |
| 成本透明+可中断 | 用量实时累计展示；ESC 随时中断 | Credits 实时结算 ✓；abort ✓ | 缺检查点可见性事件 |
| compaction 防 loop | **没有**：#31351 事故——compaction 后丢状态→重复同一计划→再 compaction，3 小时烧 30% 配额，至今 open | 无 compaction 计数 | 本项目必须补，这是抄 codex 时唯一不能抄的地方 |

**设计：预算/轮次耗尽从「终止条件」降级为「检查点条件」**：

1. 预算或轮次耗尽时不立即 wrap-up，先做**检查点评估**（全确定性信号，不做语义判断）：
   - a. todo 未完结；
   - b. 本 checkpoint 区间内有真实进展：新增成功写类工具调用（chapter_write/chapter_append/memory_save/plan_save 等）≥1 或作品字数增量 >0；
   - c. 续跑片未超链上限：自动续跑 ≤4 次（链总预算 ≤ 硬顶 500 万）、compaction 次数 ≤6；
   - d. wall-clock 总帽未超（长任务模式默认 180 分钟，见 P2 联动）。
2. 全满足 → **同 run 内自动续跑**：执行一次 compaction（复用现有 78% 压缩链路）→ 注入续跑指令（「预算检查点到达，已生成进展总结，从当前 todo 继续，勿复述已完成工作」）→ 刷新预算片（+100 万）与轮次片（+50 轮）→ SSE 不断开、runId 不变，作者视角任务一直在跑。
3. 任一不满足 → 走现有 wrap-up 路径（failed 可续跑，「继续执行」按钮保留作手动入口）。
4. **compaction 防 loop（#31351 教训产品化）**：相邻两次 compaction 之间若无新写类进展（条件 b 不成立）→ 禁止再次 compaction，直接 wrap-up 终止；P0 签名熔断与 P1 重复检测作为 compaction loop 的双保险。
5. **检查点可见性**：每次自动续跑 emit `run.checkpoint` 事件，前端对话流插一行系统行「检查点 2/4 · 累计消耗 210 万 · 进展：已写 4/6 章」——codex 的成本透明产品化；作者看到烧钱速度可随时 abort。

**为什么不违背「防浪费」初衷**：自动续跑的放行条件是「预算耗尽 且 有真实进展 且 todo 未完」——浪费场景（无进展反复思考）被条件 b + P0/P1 拦在门外，放行的只有「确实没干完的正事」；而 codex 式事故（compaction 后重复同一计划）被第 4 条专门拦截。

### 明确不做
- ❌ 不上调 200 万**默认**预算（但开放显式上调至硬顶 500 万，见第二节）：默认值够用且与 credits 定位一致
- ❌ 不新增全局并发闸：会话级 + 用户级（默认 2）+ 子 Agent 全局（8）三层已够
- ❌ 不做服务端语义级「任务是否在正常推进」判定：误杀率高，P0/P1 的确定性信号已足够
- ❌ 不做跨 run 的重复签名检测（续跑重复上一轮操作）：续跑路径已有 buildOrchestrationResumeNote 协作提醒 + assertOrchestrationResumeGuard 硬拦截覆盖，签名滑窗保持 run 级、不跨 run 持久化

## 四、测试与验收

1. 单测：签名重复滑窗（含「失败重试不计入连续次数」用例）、n-gram 检测滑窗（观察模式零干预断言）、wall-clock 总帽/空转帽超时路径（含「审批挂起期间空转钟归零」用例）、wrap-up 触发顺序（预算 < 轮次 < 熔断的优先级不回退）、tokenBudget clamp（下调/上调至硬顶/超硬顶被钳三用例）
2. P4 专项：检查点评估四条件逐条单测（todo 完结不续/无进展不续/续跑链超 4 不续/总帽超不续）；**compaction 防 loop 用例（相邻两次 compaction 间无写类进展 → 禁止再 compaction 直接 wrap-up）**；续跑片刷新后 SSE 不断流、runId 不变断言；`run.checkpoint` 事件载荷与前端系统行渲染
3. 回归：todo 拦截 4 次、结构熔断 3 次、提问预算 3 次、子 Agent 16k 钳制全部保持
4. 灰度：P0 直接全量（确定性信号 + 重试排除后误杀面极小）；P1 观察模式全量→干预模式按 `isAgent2FeatureEnabled` 灰度名单先行，观察一周误杀率再全量；P2 随 P0 同批上线；P4 按灰度名单先行（自动续跑涉及 credits 消耗节奏，名单内观察两周 checkpoint 触发分布与续跑后完成率再全量）
