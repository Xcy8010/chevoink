# 启创墨域数据模型与接口契约初稿

## 1. 文档目标

这份文档用于在正式开发前统一三件事：

- 核心业务实体与字段命名
- 前后端共享的关键状态枚举
- 第一轮并行开发时必须共同遵守的接口返回结构

它不是数据库最终定稿，而是：

> 在 A / B / C 三个窗口正式开工前，先把“大家说的是同一套对象”这件事定下来。

---

## 2. 命名总规则

### 2.1 实体命名

- 表名 / 资源名：复数英文，如 `users`、`novels`、`chapters`
- TypeScript 类型：单数 PascalCase，如 `User`、`Novel`、`Chapter`
- 接口路径：资源化，不混杂动作型命名

### 2.2 字段命名

- 接口字段统一使用 `camelCase`
- 数据库字段统一使用 `snake_case`
- 时间字段统一使用 UTC ISO 字符串对外返回
- 所有 ID 统一命名为 `id` 或 `xxxId`

### 2.3 通用字段

以下字段尽量在所有主实体中统一：

- `id`
- `createdAt`
- `updatedAt`
- `deletedAt`（如需要软删除）

## 6. 统一响应结构

## 6.1 成功响应

```ts
type ApiSuccess<T> = {
  success: true
  data: T
  requestId: string
}
```

## 6.2 失败响应

```ts
type ApiError = {
  success: false
  error: {
    code: string
    message: string
    fieldErrors?: Record<string, string>
  }
  requestId: string
}
```

要求：

- 前后端统一使用 `requestId`
- 用户可读文案放在 `message`
- 字段错误放在 `fieldErrors`

## 8. 模块目录建议

## 9. 第一轮窗口边界提示

### A 窗口

只负责：

- 设计 token

### B 窗口

只负责：

- `src/features/discover`

### C 窗口

只负责：

- `server/modules/*`

---

## 10. 最终结论

正式开工前，真正最需要统一的不是“每个人喜欢怎么写”，而是：

1. **核心实体叫什么**
2. **字段怎么命名**
3. **接口统一返回什么结构**
4. **第一轮谁能改哪些目录**

只要这份初稿先定下来，第一轮 A / B / C 三个窗口就能明显减少冲突和返工。
