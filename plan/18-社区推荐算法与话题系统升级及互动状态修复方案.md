## 一、社区帖子流推荐算法重构

### 1.1 产品定义

- **推荐 tab**：热度排序，"新帖有机会、老帖不霸榜、单次互动不引起可感知跳位"。
- **最新 tab**：严格 `createdAt desc`，不掺任何权重。
- **发帖后（仅对个人有效）**：发布成功 → 自动切到「最新」tab 并回到顶部，自己的新帖天然在第一条。不在「推荐」里做假置顶，刷新后一切按算法来。

### 1.2 排序算法（服务端统一）

排序从前端挪到服务端，`GET /api/posts` 新增 `sort=recommended|latest`（默认 recommended）。

**推荐分公式（Reddit/HN gravity 变体 + 对数压缩）**：

```
engagement = log2(1 + likeCount*3 + commentCount*4 + favoriteCount*5)
ageHours   = (now - createdAt) / 3600s
hotScore   = engagement / (ageHours + 2)^1.3
```

设计要点（对应跳位问题的三重防线）：

1. **对数压缩**：`log2(1+x)` 让"多 1 个赞"在分值上的边际影响极小——10 赞 vs 11 赞的分差 ≈ 0.06，几乎不可能因为你自己那一票翻转两个帖子的先后。这是治"我点赞它就跳上去"的核心手段。
2. **时间衰减**：`(ageHours+2)^1.3`，指数取 1.3（比首页书籍榜的 1.4 略缓，社区帖生命周期短、流量小，衰减太猛会让页面空转）。新帖 2 小时内有约 1.7 倍的天然加成窗口。
3. **确定性 tie-break**：同分按 `createdAt desc, id desc` 兜底，任何两次查询顺序稳定，杜绝"同分乱序"造成的伪跳位。

**实现方式**：帖子量当前在千级以内，直接在 `listPostsData` 内存计算排序即可（取 `where` 命中的全集 → 算分 → 排序 → 切页）；无需物化列。预留演进路径：帖子破 5 万后再落 `hotScore` 冗余列 + 定时任务刷新。

**分页一致性（防翻页重复/丢帖）**：推荐流改为**快照式游标**——第一页请求时服务端计算并返回 `snapshotAt`（服务器时间戳），后续页带上该参数，服务端只对 `createdAt <= snapshotAt` 的帖子算分排序。同一轮浏览中榜单冻结，翻页绝不因中途有人点赞而错位；下拉刷新 / 重新进入页面时丢弃 snapshot 重新计算——这正是用户要的"刷新后才按算法重排"。

### 1.3 前端改造

- `CommunityPage.tsx`：删除 L97-106 的客户端排序，tab 切换映射为 `sort` 参数，queryKey 变为 `['community','posts',activeTopicId,sort]`。
- 点赞/收藏后仅走既有 `patchPostInCaches` 更新计数与 viewer 状态，**列表顺序永不因交互实时重排**（缓存里的 pages 顺序保持不动）。
- 发帖成功回调：`setActiveTab('latest')` + `scrollTo(0)` + invalidate `['community','posts']`；「最新」流首条即自己的新帖。

### 1.4 涉及文件

| 文件 | 改动 |
|------|------|
| `api/lib/data-access.ts` | `listPostsData` 增加 sort/snapshotAt 参数与打分排序 |
| `api/routes/posts.ts` | 路由透传 sort/snapshotAt，响应携带 snapshotAt |
| `shared/contracts/api.ts` | 请求/响应契约补字段 |
| `src/pages/CommunityPage.tsx` | 删客户端排序、tab→sort、发帖后切最新 tab |

## 二、全站评论与榜单排序产品级优化

### 2.1 排序策略矩阵（一处一策，不搞一刀切）

| 场景 | 现状 | 目标策略 | 理由 |
|------|------|----------|------|
| 帖子内评论（顶层） | 时间倒序 | **热门优先**：`likeCount*2 + replyCount + 新鲜度奖励` 降序 | 论坛场景，优质讨论应上浮 |
| 评论下的回复（楼中楼） | 时间倒序 | **时间正序**（`createdAt asc`） | 回复是对话流，正序才读得通——这是 X/微博/B 站的一致做法 |
| 作品详情页书评 | 时间倒序 | **优质优先**：`likeCount*3 + replyCount*2` + 软时间衰减 | 书评是长决策内容，赞代表公信力 |
| 阅读页章节评论 | 时间倒序 | **热门优先**（同帖子评论公式） | 章评有讨论属性 |
| 段落评论（段评） | 段内时间倒序 | 段内**热门优先**，同分时间正序 | 段评短平快，高赞即共鸣点 |
| 首页/发现页各榜单 | 服务端 gravity + 前端二次重排 | **服务端单一事实源**，前端只渲染 | 消灭双轨算法 |

**新鲜度奖励**（评论热门公式中）：`freshBonus = max(0, 48 - ageHours) / 48 * 2`，即 48 小时内的新评论最多获得 +2 的分数加持，保证热评区不被半年前的老评论永久锁死，新声音有露出窗口。

### 2.2 评论排序实现

- `listCommentsData` 增加 `sort` 内部策略：按 `targetType`（novel/chapter/post/paragraph）自动选用上表策略，**接口不暴露排序参数**，产品策略收敛在服务端一处。
- 顶层评论与回复分开处理：顶层按热门分排序，`replies` 子查询固定 `createdAt asc`。
- 评论量目前为百/千级，与帖子同理走内存打分，无需索引改造。

### 2.3 首页/发现页榜单收敛

- 保留 `getHomePayloadData` 的 gravity 公式为**唯一算法**：`hotScore = (阅读*1 + 赞*3 + 评*4 + 藏*5 + 规模分) / (ageDays+2)^1.4`；完结榜维持 totalScore 无衰减（完结作品比拼总积累，合理）。
- 删除 `useHomeData.ts` 中 `rankHotPosts` 的客户端重排逻辑，前端按服务端返回顺序直接渲染。
- 榜单响应加 **60 秒服务端内存缓存**（Map + 时间戳即可，无需 Redis）：榜单短期稳定既是性能优化也是产品体验——用户来回切页不应看到榜单闪变。

### 2.4 涉及文件

`api/lib/data-access.ts`（listCommentsData、getHomePayloadData 缓存）、`src/features/home/useHomeData.ts`（删 rankHotPosts）、评论展示组件无需改动（顺序由接口决定）。

## 三、X 式话题系统升级

### 3.1 产品定义（对标 X / Twitter Hashtag）

1. 发帖时在正文中输入 `#话题名`（空格/标点/换行结束）即引用话题；话题不存在则**发布时自动创建**。
2. 帖子内 `#话题` 渲染为可点链接（品牌色文本，无背景无边框），点击进入**话题详情页**。
3. 话题详情页：话题名 + 帖子数统计 + 「热门 / 最新」双 tab 的帖子流（复用第一章的排序能力）。
4. 发讨论弹窗：**删除全部预设话题按钮**，改为一行安静的引导文案 + 三个算法推荐话题，点击话题名直接把 `#话题名 ` 插入编辑区光标处。

### 3.2 数据模型

```prisma
// 帖子 ↔ 话题 多对多（一条帖子可带多个 #话题）
model PostTopic {
  postId    String
  topicId   String
  createdAt DateTime @default(now())
  post      Post     @relation(fields: [postId], references: [id], onDelete: Cascade)
  topic     Topic    @relation(fields: [topicId], references: [id], onDelete: Cascade)
  @@id([postId, topicId])
  @@index([topicId, createdAt])
}
```

- 既有 `Post.topicId` 单外键**保留不删**（兼容旧数据与现有筛选），发布时同步写入 PostTopic;首个解析到的话题回填 topicId。
- Topic 沿用现有模型，`postCount` 改由 PostTopic 聚合维护（发帖 +1，删帖 -1）。

### 3.3 # 解析规则（服务端为准，前端仅高亮）

```
正则：#([\p{L}\p{N}\u4e00-\u9fa5_]{1,24})
```

- `#` 后跟 1-24 个汉字/字母/数字/下划线，遇空格、标点、换行、下一个 `#` 终止。
- **发布时由服务端解析**正文（标题不参与），`upsert` 话题（按 name 去重，slug 用 name 的 URL-safe 编码），写 PostTopic 关联，单帖最多关联 5 个话题（防刷）。
- 前端渲染帖子正文时用同一正则把 `#xxx` 替换为 `<Link to="/community/topic/:slug">`，其余文本原样输出。解析逻辑放 `shared/` 侧共享，保证前后端行为一致。

### 3.4 推荐话题算法（弹窗内 3 个）

```
GET /api/topics/recommended  →  Top 3
trendScore = 近7天新增帖子数 * 3 + log2(1 + 总帖子数)
```

- 近 7 天权重占大头 → 推的是"正在被讨论的话题"而不是历史总量榜，符合"推荐"的运营心智；`log2` 总量项保证冷启动期（大家都没发帖）仍有稳定兜底。
- 同分 tie-break：`lastUsedAt desc`（PostTopic 最新 createdAt）。
- 接口带 60 秒内存缓存，与榜单缓存同一套工具。

### 3.5 UIUX 规范（严禁 AI 质感、严禁容器套容器）

**发讨论弹窗底部区域**——只有两行纯文本，零卡片零胶囊零边框：

```
使用 # 可以引用或创建一个话题                ← text-xs, var(--text-tertiary)
推荐话题  #都市脑洞  #新人求评  #今日更新      ← 话题为品牌色纯文本链接，hover 加深，点击插入编辑区
```

- 两行之间 8px 间距，与编辑区之间用 12px 呼吸留白分隔，**不加分割线、不加背景色块**。
- 点击推荐话题：在 textarea 当前光标处插入 `#话题名 `（带尾随空格），并保持焦点在编辑区——用户手不离键盘的连贯感。
- 正文输入时对 `#xxx` 做实时品牌色高亮（overlay 高亮层或轻量方案：仅在预览态高亮，输入态不做，避免 contenteditable 复杂度——**采用后者**，输入态不高亮，为工程稳健让步）。

**帖子卡片内**：`#话题` 就是正文中的品牌色文字链接，不做成 chip/标签块——这正是 X 的做法，信息密度最高、最无"AI 质感"。

**话题详情页**（`/community/topic/:slug`）：

```
← 返回      #都市脑洞                    ← 大标题直接排版，无 hero 卡片
            1,024 帖子                   ← text-xs 次要色
────────────────────────────
热门  最新                               ← 与作者页一致的下划线 tab
[帖子流，复用 PostCard]
```

- 页面骨架复用社区页布局，仅头部三行文字 + tab + 流，不新增任何包裹容器。

## 五、点赞/收藏状态回显修复（P0 Bug）

### 5.1 根因

`getViewerPostFlags`（批量查 postLike/postBookmark）+ `attachPostViewerFlags`（附加 `likedByViewer/bookmarkedByViewer`）这套现成机制只在 `listPostsData` 用了，三个个人中心/作者页数据函数漏用：

| 函数 | 位置 | 问题 |
|------|------|------|
| `listUserLikedPostsData` | data-access.ts L2341-2364 | 直接 `toPost(record.post)`，flags 恒为 false |
| `listUserBookmarkedPostsData` | L2367-2389 | 同上 |
| `listUserRepliesData` | L2392-2443 | UserReplyItem 完全无 viewer 状态字段 |

### 5.2 修复

1. `listUserLikedPostsData` / `listUserBookmarkedPostsData`：查询后统一走 `getViewerPostFlags(viewerId, postIds)` → `attachPostViewerFlags`，与 `listPostsData` L1679-1685 完全同款三行。注意 viewerId 取**当前登录用户**而非被浏览的主页主人——去别人作者页看 TA 的喜欢列表时，icon 亮不亮取决于"我"是否赞过。
2. `listUserRepliesData`：返回项补 `likedByViewer`（评论自身的点赞态）及所属帖子的 viewer flags，契约 `UserReplyItem` 同步加字段。
3. 顺带审计：全项目 `toPost(` 调用点逐一过一遍，凡是返回给登录用户的帖子列表一律确保挂 flags，杜绝第四处漏网。
4. 前端零改动：PostCard 的高亮判定（`post.likedByViewer` / `post.bookmarkedByViewer`）本来就是对的，数据对了 icon 自然对。个人中心与作者页共用接口，一次修复两处生效。

## 八、风险与取舍备忘

- **内存排序上限**：帖子/评论均为内存打分排序，量级 5 万以内无压力；超过后按 1.2 节预留路径落冗余列。当前阶段不为未来规模预付复杂度。
- **快照游标**：snapshotAt 仅约束推荐流翻页，不引入服务端会话状态（无状态参数往返），PM2 多实例也安全。
- **# 解析安全**：正则限长 24 字符 + 单帖 5 话题上限 + 服务端为准，防话题灌水；slug 冲突用 name 唯一约束兜底。
- **Post.topicId 兼容**：保留旧字段避免一次性数据迁移风险，PostTopic 与其并行；后续话题系统稳定后再评估废弃。
- **输入态 # 不做实时高亮**：为避免 contenteditable/overlay 的工程复杂度与移动端输入法兼容坑，首版仅发布后渲染高亮，属主动取舍。
