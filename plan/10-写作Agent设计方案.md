# 启创墨域写作 Agent 设计方案

> 修订记录：2026-07 v1.1 —— 与《13-创作区Agent深度重构与前端产品级优化方案》对齐：
> 工具层升级为“Schema + 执行器 + 权限”三位一体并由原生 Function Calling 驱动（见 10.3 / 14 节修订说明）；
> 新增写作 Agent 的动作与决策能力清单（全书检索、角色卡/伏笔/时间线工具、澄清提问、长任务清单等，见第 19 节）。
> 阅读顺序建议：本文（产品定位与记忆体系）→ 11 号（opencode 方法论）→ 13 号（最终执行方案）。

## 1. 文档目标

本文用于在 `启创墨域 ChevoInk` 现有产品与技术边界内，设计一套可落地的“写作 Agent”方案。

约束前提不变：

- 只允许本地运行，不做公网部署改动
- 所有 AI 调用必须走本地后端
- 真实 API Key 仅允许保存在服务端 `.env`
- 不把产品做成一个脱离创作工作台的泛聊天工具
- 不推翻现有 UI/UX 定位，只在创作中心内做能力增强

---

## 2. 为什么 ChevoInk 需要 Agent，而不是普通 AI 输入框

ChevoInk 的核心不是“一次性生成一段文案”，而是持续完成以下闭环：

1. 管理小说项目、章节、设定与发布状态
2. 在长周期创作中维持人物、世界观、时间线一致性
3. 把 AI 结果接入真实编辑流程，而不是停留在聊天结果页
4. 让创作、修订、封面、发布形成连续工作流

普通聊天框的上限很快出现：

- 不知道当前正在处理哪本书、哪一章、哪个角色
- 不知道哪些内容是“设定”，哪些是“草稿”，哪些已发布
- 无法稳定维护长篇上下文
- 产出结果与正文编辑器、章节结构、封面流程脱节

因此，ChevoInk 需要的不是“更会聊天的助手”，而是“嵌在创作工作台里的任务型写作 Agent”。

## 3. 外部参考与取舍

## 3.1 重点参考项目

### `opencode`

可借鉴：

- `Plan / Build` 双模式
- 主 Agent + 子 Agent 的分工方式
- `AGENTS.md` / 项目级规则注入
- 多会话切换与任务隔离

不直接照搬：

- 它偏代码工作流，ChevoInk 需要的是小说项目工作流
- 终端导向交互不适合直接成为最终用户主界面

### `Cline`

可借鉴：

- `Plan / Act` 强切分
- rules / skills 体系
- checkpoint / undo 思路
- 多 Agent 协作与人工确认机制

不直接照搬：

- ChevoInk 不能把每次写作都变成“工具审批流”
- 需要更强的作品结构感，而不是 IDE 操作感

### `NovelForge`

可借鉴：

- 多 Agent 协作写作
- Writer / Editor 辩论式修订
- Working / Episodic / Semantic 三层记忆
- Orchestrator + Message Bus + Blackboard 结构

不直接照搬：

- 其目标更接近“全自动整本生成”
- ChevoInk 第一阶段应坚持“人主导，Agent 辅助”

### `Morpheus`

可借鉴：

- 面向长篇创作的工作台思路
- 章节优先的创作与修改流程
- 长上下文压缩与连续性维护
- 轨迹回放、可审阅过程

不直接照搬：

- ChevoInk 当前不需要引入过重的全量轨迹系统
- 先做创作中心内的轻量运行记录和版本快照

### `AuthorClaw`

可借鉴：

- 技能化能力组织方式
- 从大纲、正文、修订到营销文案的任务模板
- persona / style profile 的写作风格配置

不直接照搬：

- 它更像完整“自动出书流水线”
- ChevoInk 当前重点仍是小说创作工作台，不是全链路出版运营后台

## 3.2 结论

ChevoInk 应采用：

- `opencode / Cline` 的模式控制与规则体系
- `NovelForge / Morpheus` 的写作多 Agent 与记忆结构
- `AuthorClaw` 的技能化任务封装

但必须避免：

- 全自动整书生产
- 脱离编辑器的独立聊天产品
- 过重、过长、过技术化的操作界面

## 4. 产品定位

ChevoInk 写作 Agent 的定位是：

> 一个嵌入创作中心的、面向中长篇小说写作的任务型协作 Agent 系统。

它不是：

- 通用问答机器人
- 纯聊天陪伴角色
- “一句话生成整本书”的黑盒

它应该帮助作者完成四类核心任务：

1. 规划：设定、大纲、章节计划、伏笔铺排
2. 生成：起草章节、续写、改写、润色、生成摘要
3. 审阅：一致性检查、节奏检查、角色行为检查
4. 整理：沉淀作品记忆、维护设定资产、沉淀可复用风格

---

## 5. 总体设计原则

1. 人主导，Agent 协作  
   Agent 可以提议、生成、修订，但不应默认越过作者直接发布。

2. 工作台优先，聊天次之  
   聊天只是交互方式，核心是对“当前小说项目”的操作。

3. 计划先于执行  
   大任务先计划，再生成；避免直接把长篇创作变成随机输出。

4. 结果必须可落回正文  
   每次生成结果都必须可以追加、替换、另存版本或摘取片段。

5. 长上下文依赖结构化记忆，而不是无限堆历史消息  
   必须做章节级、项目级、作品级的压缩与检索。

6. 安全与权限优先  
   所有模型调用、提示拼装、日志脱敏、配额统计都在后端统一完成。

## 6. Agent 架构

## 6.1 角色分层

建议采用“1 个主控 Agent + 5 个专职子 Agent”的结构。

### 主控 Agent

`Writing Orchestrator`

职责：

- 理解用户意图
- 判断属于规划、生成、修订还是检查任务
- 组装上下文
- 选择是否调用子 Agent
- 汇总结果并返回可执行动作

### 子 Agent

`Story Planner`

- 负责题材拆解、故事骨架、章节规划、伏笔建议

`Draft Writer`

- 负责正文起草、续写、扩写、场景重写

`Continuity Editor`

- 负责人物设定、世界观、时间线、一致性检查

`Style Editor`

- 负责语气、节奏、文风、句式层面的润色

`Lore Librarian`

- 负责从小说、章节、角色、设定中提取和归档长期记忆

`Cover Prompt Agent`

- 负责从作品信息提炼封面提示词，供现有封面链路使用

## 6.2 为什么不在第一阶段做更多 Agent

第一阶段不建议继续拆成十几个角色，原因很现实：

- 调度复杂度会明显上升
- 上下文拼装和费用控制更难
- 调试成本高，不利于本地联调

第一阶段先保证：

- 有主控
- 有规划
- 有生成
- 有一致性
- 有文风修订

这套闭环已经足够支撑创作工作台的产品价值。

## 7. 工作模式设计

## 7.1 三种模式

### `Plan`

只分析，不直接改正文。

适用任务：

- 生成大纲
- 规划章节
- 分析当前章节问题
- 设计下一章推进方案

输出形态：

- 章节计划
- 场景清单
- 冲突与目标建议
- 修订建议列表

### `Act`

直接生成或改写可落回正文的内容。

适用任务：

- 起草章节
- 续写当前段落
- 重写某个场景
- 润色某一段

输出形态：

- 可直接插入正文的文本
- 带差异说明的替换版本

### `Review`

不负责新写内容，专做检查。

适用任务：

- 人物行为是否前后冲突
- 设定是否撞车
- 节奏是否过慢
- 信息是否重复

输出形态：

- 问题清单
- 证据片段
- 修复建议

## 7.2 模式切换原则

- 大任务默认先 `Plan`
- 小范围改写可直接 `Act`
- 发布前建议至少经过一次 `Review`

## 8. 记忆体系设计

ChevoInk 不应只保存聊天记录，而应保存“可用于下次写作的结构化记忆”。

## 8.1 四层记忆

### L0：运行态上下文

当前会话即时上下文，包括：

- 当前小说
- 当前章节
- 当前选中文本
- 本轮用户意图

特点：

- 生命周期最短
- 只服务当前一次请求

### L1：工作记忆

当前章节附近的高相关内容，包括：

- 本章正文
- 上一章摘要
- 下一章计划
- 当前角色状态

特点：

- 面向“正在写这一章”
- 由后端在请求前动态拼装

### L2：项目记忆

面向整本小说的结构化资产，包括：

- 小说简介
- 世界观设定
- 角色卡
- 章节摘要
- 时间线
- 伏笔表
- 风格偏好

特点：

- 是长篇一致性的核心
- 需要长期持久化

### L3：语义记忆

从全书中抽取的可检索知识片段，包括：

- 角色关系事实
- 场景设定事实
- 关键事件事实
- 已明确禁忌设定

特点：

- 用于长上下文下的召回
- 可以结合向量检索或标签索引

## 8.2 记忆写入原则

不是每轮对话都写入长期记忆，只沉淀高价值信息：

- 用户确认过的设定
- 已保存的大纲与章节摘要
- 角色关系变化
- 重要伏笔与回收
- 明确的风格偏好

避免把噪音写进去：

- 临时试写
- 未确认构想
- 失败的生成结果

---

## 9. 上下文组装策略

后端统一通过 `Context Manager` 组装上下文，顺序建议如下：

1. 系统规则  
   产品边界、安全规则、当前模式

2. 用户意图  
   用户输入、显式目标、选中文本

3. 当前工作对象  
   小说信息、当前章节、章节状态

4. 高相关工作记忆  
   上一章摘要、下一章计划、角色状态

5. 项目级结构化记忆  
   设定、角色卡、时间线、伏笔

6. 语义召回片段  
   从全书知识中检索最相关事实

7. 输出约束  
   输出格式、可执行动作、长度要求

当上下文过长时，优先压缩顺序：

1. 历史消息
2. 低相关摘要
3. 大段正文原文

不能被轻易压缩的内容：

- 当前选中文本
- 当前章节目标
- 已确认设定
- 用户本轮明确指令

## 10. 工具层设计

Agent 不直接操作数据库，而是调用后端受控工具。

## 10.1 基础工具

`getNovelContext(novelId)`

- 获取小说基础信息、设定摘要、风格偏好

`getChapterContext(novelId, chapterId)`

- 获取当前章节、邻近章节摘要、章节计划

`searchProjectMemory(novelId, query)`

- 检索角色、设定、时间线、伏笔等结构化记忆

`saveAgentDraft(novelId, chapterId, content, mode)`

- 保存 Agent 生成草稿或候选版本

`applyDraftToChapter(chapterId, content, strategy)`

- 以追加、替换、插入等方式写回正文

`createMemoryEntry(novelId, type, payload)`

- 沉淀角色、设定、章节摘要、事件等记忆

`generateCoverPrompt(novelId)`

- 调用已有封面提示词链路

## 10.2 工具调用原则

- 所有工具调用必须有 `userId`
- 所有操作必须绑定 `novelId`
- 对已发布内容的写操作必须更谨慎
- 任何“发布”操作都不能由 Agent 默认自动触发

## 10.3 2026-07 修订说明

10.1 的函数式工具清单在 13 号方案中落地为带 zod Schema、execute 执行器与模式级权限的统一注册表，并由模型通过原生 tool_calls 自主调用（而非系统按预制模板代调）；读写分离是关键增量——模型写作前先自主读取上下文。完整工具抽象见 13 号方案 4.2；本文新增的动作与决策能力见第 19 节。

## 11. 前端嵌入方式

## 11.1 不新开独立产品

写作 Agent 必须嵌入现有 `StudioWorkspace`，而不是额外做一个新站点或新主导航。

## 11.2 推荐界面结构

保持现有工作台结构，只增强右侧和局部底部：

- 左栏：章节树、项目结构
- 中栏：正文编辑区
- 右栏：Agent 面板
- 底部可折叠：运行记录 / 草稿版本 / 检查结果

## 11.3 右栏 Agent 面板建议

右栏分为 4 个标签：

1. `计划`
2. `写作`
3. `审阅`
4. `封面`

每个标签只放少量高频动作，不做复杂表单墙。

示例动作：

- 生成本章计划
- 为当前标题起草正文
- 续写选中段落
- 检查人物一致性
- 提炼封面提示词

## 11.4 结果落地方式

每次 Agent 结果必须提供明确动作：

- 插入到光标处
- 替换选中内容
- 另存为候选版本
- 复制到草稿区
- 存为章节计划

不应只停留在“聊天气泡”里。

## 12. 后端架构设计

## 12.1 新增核心模块

建议在后端新增以下逻辑层：

- `agent-orchestrator`
- `context-manager`
- `agent-memory-service`
- `agent-run-service`
- `ai-provider-adapter`

## 12.2 运行流

```text
Frontend Studio
  -> /api/agent/runs
  -> Agent Orchestrator
  -> Context Manager
  -> Selected Agent / Subagent
  -> AI Provider Adapter
  -> Stream result / save artifacts
  -> optional memory extraction
```

## 12.3 流式返回

建议 Agent 结果使用 SSE 返回，原因：

- 适合正文渐进生成
- 适合展示执行步骤
- 适合在右栏显示“规划中 / 写作中 / 审阅中”

## 12.4 日志与审计

至少记录：

- `runId`
- `userId`
- `novelId`
- `chapterId`
- `mode`
- `agentType`
- token 使用量
- 耗时
- 结果状态

日志中不能保存：

- 明文 API Key
- 未脱敏 provider 返回头

## 13. 数据模型建议

在现有 `Conversation / Message / AiUsageLog` 基础上，建议新增以下实体。

## 13.1 `AgentSession`

表示某本小说下的一个 Agent 会话。

建议字段：

- `id`
- `userId`
- `novelId`
- `title`
- `status`
- `lastRunAt`
- `createdAt`
- `updatedAt`

## 13.2 `AgentRun`

表示一次具体执行。

建议字段：

- `id`
- `sessionId`
- `chapterId`
- `mode`
- `agentType`
- `status`
- `inputSummary`
- `outputSummary`
- `startedAt`
- `finishedAt`

## 13.3 `AgentArtifact`

表示某次执行产生的结果物。

建议字段：

- `id`
- `runId`
- `artifactType`
- `title`
- `content`
- `metadata`
- `createdAt`

可用于保存：

- 章节计划
- 候选正文
- 审阅报告
- 风格建议

## 13.4 `ProjectMemoryEntry`

表示项目长期记忆。

建议字段：

- `id`
- `novelId`
- `memoryType`
- `title`
- `content`
- `sourceChapterId`
- `importance`
- `embeddingRef`
- `createdAt`
- `updatedAt`

- `POST /api/agent/actions/plan-chapter`

- 第一阶段优先模板动作接口，少做完全自由形态 Agent

## 15. 第一阶段最小可落地版本

## 15.1 P0 能力范围

只做以下能力：

1. 章节计划生成
2. 章节起草
3. 选中文本续写 / 改写 / 润色
4. 一致性审阅
5. 封面提示词提炼
6. 候选结果保存与应用
7. 章节摘要自动沉淀

## 15.2 P0 不做

- 自动批量生成整本书
- 自动发布
- 全量多 Agent 可视化编排
- 复杂多轮辩论 UI
- 对外协作、多人实时写作
- 公开云端项目共享

## 15.3 为什么这样切

因为 P0 的目标不是“炫技”，而是先把以下体验做顺：

- 用户能在当前工作台里稳定调用 Agent
- 生成结果能顺手落回正文
- 长篇写作不会因为上下文漂移迅速失控

## 17. 风险与控制

## 17.1 风险：Agent 产出过度自由，污染正文

控制：

- 默认先落为候选版本
- 替换正文需要显式确认

## 17.2 风险：长篇上下文失真

控制：

- 用章节摘要、角色状态、时间线维护结构化记忆
- 不依赖无上限消息历史

## 17.3 风险：后端接口失控，泄露敏感配置

控制：

- Provider 适配层统一出口
- URL 白名单、模型白名单、日志脱敏

## 17.4 风险：UI 变重，破坏当前工作台气质

控制：

- Agent 面板只做任务入口
- 不增加大面积“聊天产品化”容器

---

## 18. 最终结论

ChevoInk 的写作 Agent，不应做成一个泛 AI 聊天框，也不应一开始就走向“全自动出书工厂”。

更合适的路线是：

- 用 `opencode / Cline` 的模式与规则体系控住行为
- 用 `NovelForge / Morpheus` 的写作多 Agent 与长记忆结构解决长篇一致性
- 用 `AuthorClaw` 的技能化任务模板提升执行效率
- 最终把这些能力收敛到 `StudioWorkspace` 内，成为创作工作台的一部分

一句话概括：

> 第一阶段把它做成“会规划、会起草、会审阅、能落回正文”的写作 Agent；而不是“会聊天但不接工作流”的 AI 面板。

## 19. 2026-07 修订增补：新增动作与决策能力

## 19.1 为什么需要新增

原第 10 节工具面向“取上下文 → 落草稿”的最小闭环，实施调研（见 13 号方案 2.1）后确认缺三类能力：

1. **作品资产的结构化操作**：角色卡、伏笔、时间线只能被动抽取，模型无法主动登记与回收
2. **全书级检索**：一致性审阅没有“grep”，只能靠把正文塞进上下文硬扫
3. **Agent 的元决策动作**：不确定时只能猜（无澄清提问），长任务无法自管理进度（无任务清单）

## 19.2 新增动作（工具）

以下工具统一纳入 13 号方案 4.2 的工具抽象（zod Schema + execute + 模式级权限）：

| 工具 | 作用 | 典型触发场景 | 阶段（对齐 13 号） |
|---|---|---|---|
| `ask_user` | 澄清提问：选项式问题（附 2~4 个选项），复用审批的暂停-恢复通道 | 用户说“写一章”但人称/视角/篇幅未定且影响整章走向 | P1 |
| `novel_search` | 全书正文关键词检索（返回章节+片段），一致性校对的“grep” | 写作前校对人名/地名/设定；Review 模式找矛盾证据 | P2 |
| `character_card_upsert` / `character_card_get` | 角色卡结构化维护（外貌/性格/关系/当前状态） | 新角色登场、角色状态发生关键变化 | P2 |
| `foreshadow_register` / `foreshadow_resolve` | 伏笔台账：埋设时登记、回收时销账，未回收项可被检索 | 计划/写作中埋设伏笔；审阅时扫描未回收伏笔 | P2 |
| `timeline_event_add` | 时间线事件登记（章节锚点 + 相对时序） | 关键事件落笔后沉淀，供时序一致性检查 | P2 |
| `todo_write` | Agent 自管理任务清单（项目：内容/状态），前端渲染为进度清单卡片 | 跨 ≥2 章的批量任务先分解再逐项执行，中断可续 | P2 |
| `chapter_move` / `chapter_delete` | 章节结构管理（排序/删除，删除全模式 `ask`） | “把番外移到第五章后”“删掉废稿章” | P1 |
| `novel_stats` | 字数/章节数/更新节奏统计 | 回答“写了多少了”、规划篇幅时参考 | P3 |

## 19.3 新增决策策略（写进模式契约，而非穷举规则）

以下六条行为准则作为 system prompt 的“模式契约”段落（每条一句话），配合工具权限约束，不得退化为穷举 if/else 规则：

1. **澄清优先于猜测**：影响整章走向的关键设定缺失时先 `ask_user`；一次只问一个问题，小于段落级的不确定直接按作品风格处理
2. **写前必读**：任何正文写入前至少完成一次相关读取（`chapter_read` / `memory_search` / `novel_search`），禁止盲写
3. **模式自适应**：Build 收到纯规划类请求时先短规划再执行；Plan 收到执行请求时产出计划并 `plan_exit` 交接，不越权直接执行
4. **长任务先分解**：跨 ≥2 章的任务先 `todo_write` 拆解，逐项执行、逐项汇报，中断后可从清单续跑
5. **记忆沉淀有时机**：新角色登场、设定被用户确认、伏笔埋设/回收时调对应资产工具；试写与未确认构想不沉淀（对齐 8.2 节）
6. **一致性防线前移**：写作前用 `novel_search` + `memory_search` 校对人名/地名/已有设定，而不是只靠事后 Review 兜底

## 19.4 与 13 号方案的关系

本节工具与决策策略是 13 号方案工具注册表与 prompt 体系的增量扩充：`ask_user` 并入 13 号 P1（复用审批信箱基础设施）；资产工具、`novel_search`、`todo_write` 并入 13 号 P2（与记忆体系同期）；`novel_stats` 并入 P3。决策策略作为 13 号 4.4 节“模式契约”的正式内容，随 P1 一同落地。
