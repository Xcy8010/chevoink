## 一、现状复盘：本次"第七章规划"任务暴露的五类问题

以下问题均在同一次真实任务（Plan 模式，"帮我规划第七章"，9 轮 / 96,920 tokens）中复现，且每一类都能定位到明确的代码层根因。

### P1 思考独白泄漏到对话正文（幻觉·信道混淆）

**现象**：正文出现"先全面梳理第六章结尾和所有伏笔，再做规划""信息已全面掌握。现在制定第七章规划并落盘""方向明确。现在制定第七章完整规划并落盘"等过程旁白——这些是给自己看的执行叙述，不是给作者看的结论。

**根因**：
- 模型的 reasoning 信道（思考过程折叠区）与 content 信道（正文）由模型自己决定写入哪边，DeepSeek 系模型在多轮工具循环中习惯在每轮 content 开头"报幕"。
- `context.ts` 的 IDENTITY_PROMPT 只约束了"收尾总结简短"和"禁止内心独白"（上一轮已加），但没有约束**中间轮次**的正文输出——工具循环的每一轮都会产生一段 content，这些零碎旁白全部被前端渲染出来。
- Loop 层（loop.ts）对中间轮次的 text 无任何过滤或约束机制，模型每轮说什么就流式推什么。

### P2 伪工具调用：把调用写进正文再道歉（幻觉·执行虚构）

**现象**：模型先在正文里"演"了一次工具调用（文本模拟），随后自己发现并输出"抱歉，立即补上真正的工具调用"，思考过程里写"我需要用真正的 function calling 来发起工具调用，而不是在文本中模拟"。

**根因**：
- loop.ts 已有伪工具调用检测（`pseudoToolCallRetries`），但正则只匹配 `[调用工具 …]` 这一种历史压缩标记格式；模型换一种写法（如代码块、"我现在调用 plan_save：{...}"）就漏检。
- 检测触发后回填的系统提示生效了（模型道歉并补真调用），说明机制有效但覆盖面不足——本次是模型**自愈**而非护栏拦截。

### P3 计划概览全文粘贴到正文（提示词失效）

**现象**：plan_save 已落盘 2240 字计划后，正文又输出了完整的"第七章《九号舱》规划概览"长文 + "需要你确认的方向性选择：1. R4是敌是友？…"多条问题列表。

**根因**：
- plan_save 的 output 回填里写了"回复中只需简短说明规划要点，不要重复粘贴计划全文"，但"简短说明规划要点"给了模型太大解释空间——它把 500+ 字概览也理解成"要点"。
- 落盘后模型又在正文里罗列方向性问题，这正是 ask_user 工具要接管的场景——说明 Plan 模式契约里"禁止正文罗列问题选项"的约束在长上下文（97k tokens）下权重被稀释。

### P4 重复提问 + 每次回答后重新生成新计划而非修改原计划

**现象**：ask_user 提问 → 回答 → 生成计划 → **又二次、三次提问** → 每次回答后都调 plan_save 生成一个**全新**的"第七章规划"，作品树计划文件夹出现两个同名文件。

**根因（这是本次最硬的一个工程缺陷）**：
- `write-tools.ts` 的 planSaveTool **只会 `prisma.agentArtifact.create`**，参数里没有"更新已有计划"的能力（无 planId/artifactId 参数，也不按 novel+title 去重）。模型即使想"修订原计划"也无工具可用，只能再存一份。
- ask_user 没有次数预算：提示词允许"关键意图不明时提问"，但没约束一次任务最多问几次、也没约束"拿到回答后应修订而非重建"。
- 后端 `listNovelPlanArtifacts` 按 createdAt 罗列全部 savedAsPlan 产物，同名不合并，前端树里自然出现重复项。

### P5 计划写入无人工审查（能力缺失）

**现象**：章节正文变更有绿色 ✓ / 红色 ✕ 的待审查条（pendingReview，批准/撤销），但 plan_save 直接落盘，作者无法像审正文一样审计划的新增/修订。

**根因**：
- `ChapterPendingReview` 链路（types.ts / StudioWorkspace / AgentPanel 审查条）只为章节 diff 设计；计划产物走的是 planFile display + 树节点直挂，没有 before/after 与批准/拒绝语义。
- 计划被定位成"轻量产物"，但实际使用中它是后续写作的蓝本，重要性不低于正文，理应有同级审查。

### 附：现有架构中可复用的资产

| 资产 | 位置 | 与本方案的关系 |
|---|---|---|
| Agent 声明式注册表（tools 白名单/modes） | agents.ts | Skill/子 Agent 扩展的挂载点 |
| 三段式 system prompt 组装 | context.ts | 知识集注入点 |
| L2/L3 记忆摘要（风格规则/角色卡/伏笔） | context.ts + projectMemoryEntry | 写作知识集可复用同一张表 |

| 审批/提问信箱（挂起-唤醒） | permissions.ts | 计划审查可复用同构模式 |
| 章节审查条（✓/✕） | AgentPanel + StudioWorkspace | 计划审查 UI 直接复用 |

## 二、优化方案总体架构

按"**护栏层 → 工具层 → 提示词层 → 知识层 → Skill 层 → 交互层**"六层推进，前三层治幻觉（对应 P1-P3），工具层+交互层补能力缺陷（P4-P5），知识层+Skill 层做长期的文笔与规范性提升。

```
┌─ 交互层：计划审查条（✓/✕）、提问预算 UI 提示
├─ Skill 层：章节规划 / 章节写作 / 修订 / 一致性审阅 四个内置 Skill（流程模板+检查清单）
├─ 知识层：操作知识集（怎么干活）+ 写作文笔知识集（怎么写得好，分题材）
├─ 提示词层：信道纪律重写、中间轮次旁白约束、输出模板化
├─ 工具层：plan_save 升级 upsert、plan_update 修订语义、ask_user 预算
└─ 护栏层：伪调用检测扩展、旁白熔断、Plan 模式纯文本轮次约束
```

## 三、方案 A：提示词层——信道纪律与输出模板（治 P1/P3）

### A1 IDENTITY_PROMPT 重写"信道纪律"段

把现有零散约束整合成一个明确的**双信道模型**，让模型对"什么内容进哪个信道"零歧义：

- 思考信道（reasoning）：分析、计划、自我纠错、工具选择、状态盘点（"信息已掌握""现在开始 X"）——全部只进思考。
- 正文信道（content）：只允许三种内容——①最终结论/交付说明（≤2句80字）②必须由作者决策但 ask_user 不适用的说明 ③错误或阻塞的如实告知。
- 明确列出违例句式黑名单（从本次实录提取）："先梳理…再做规划""信息已全面掌握""现在制定…并落盘""方向明确""抱歉，立即补上""让我…"等报幕式/自我修正式开场，写明"这类句子出现在正文即违规"。

### A2 中间轮次静默约束（新增段落）

现有提示词只管"收尾总结"，需补一条循环行为约束：

- "工具循环进行中的轮次，若下一步是继续调用工具，正文信道保持为空（直接发起调用），不要输出过渡性说明。只有任务结束或需要作者介入时才写正文。"

### A3 plan_save 回填话术收紧（治 P3）

- 工具 output 由"只需简短说明规划要点"改为给出**硬模板**："回复正文只允许一句话：『已把《标题》写入计划文件夹，可在左侧作品树查看和编辑。』如需作者决策请用 ask_user，禁止在正文罗列任何计划内容或问题列表。"
- MODE_CONTRACTS.plan 同步补一句："plan_save 落盘后本次规划任务即完成，不要在正文复述计划。"

### A4 长上下文权重防稀释

- 97k tokens 场景下 system prompt 约束衰减明显。在 loop.ts 每轮组装消息时，若累计上下文超过阈值（如 60k 字符），在消息队列尾部追加一条轻量 system 提醒（≤100字，只重申信道纪律+当前模式），成本极低但能显著拉回注意力。

## 四、方案 B：工具层——plan_save 升级与 ask_user 预算（治 P4）

### B1 plan_save 升级为 upsert 语义

- 参数新增 `planId?: string`（对应 artifactId）：提供则更新既有计划（title/content 覆盖，metadata 保留 savedAsPlan），不提供则新建。
- **兜底去重**：不提供 planId 时，按 `run.novelId + title` 精确匹配已有 savedAsPlan 产物；命中则自动转为更新并在 output 里告知模型"检测到同名计划，已就地更新而非新建"。双保险防止模型忘传 planId。
- 工具 description 明确："修订已有计划必须带 planId 就地更新，禁止另存一份同名计划。"
- 工具执行前通过只读上下文把当前作品的计划列表（id+title）注入（novel_get_context 返回值扩展，或 plan_save 失败信息里回传候选列表），让模型有 planId 可用。

### B2 ask_user 提问预算

- ToolContext 增加 run 级计数（内存 Map，随 finalizeRun 清理）：每个 run 最多 2 次 ask_user；超出时工具直接返回"提问次数已用完，请基于已有回答给出最终方案"，不再挂起。
- 工具 description 同步声明预算："一次任务最多提问 2 次，尽量把相关的不确定点合并成一次提问。"
- 提示词补充"回答后的行为契约"：拿到回答后必须**修订**（plan_save 带 planId）而不是重新生成。

### B3 计划产物列表去重（后端兜底）

- `listNovelPlanArtifacts` 对同 novel 同 title 的多份产物只返回最新一份（或返回全部但标记 supersededBy），历史脏数据（本次已产生的重复"第七章规划"）自动收敛，无需迁移脚本。

## 五、方案 C：护栏层——Loop 内核检测扩展（治 P1/P2 的机械防线）

提示词是软约束，护栏是硬防线，两层缺一不可。

### C1 伪工具调用检测扩展

现有正则只匹配 `[调用工具…]`。扩展为多模式检测（任一命中即回填纠正提示，复用现有 `pseudoToolCallRetries` 机制）：

- `[调用工具/tool …]`（现有）
- 正文出现工具名+参数 JSON 的组合（如 `plan_save` / `ask_user` + `{"title"` 同段出现）
- "我现在调用/发起/执行 xxx 工具"句式且本轮 finishReason ≠ tool_calls

### C2 旁白熔断（新增，轻量启发式）

- 中间轮次（finishReason === 'tool_calls'）产生的 content 若命中报幕句式（"先…再…""现在开始/制定/落盘""信息已…掌握"等，维护一个短模式表），该段文本**降级为 reasoning 事件**推送（前端进思考折叠区）而不是 text 事件。
- 不删内容、不打断循环，只是改道——对模型无感知、对作者视觉干净。误判的代价只是一句话进了思考区，风险可控。

### C3 Plan 模式纯文本轮次约束

- Plan 模式下若模型连续 2 轮 finishReason !== 'tool_calls' 且未调用过 plan_save，回填提示"规划模式的产出必须通过 plan_save 落盘，请调用工具"——防止模型全程只聊天不落盘。

## 六、方案 D：知识集——操作知识集 + 写作文笔知识集

两个知识集都注入 system prompt，但策略不同：操作知识集**全量常驻**（小而精），文笔知识集**按需检索**（大而全）。

### D1 Agent 操作知识集（怎么干活，常驻，≤600字）

新增 `api/lib/agent/knowledge/operation.ts`，以"操作守则"段落拼入 system prompt（位于 DECISION_STRATEGIES 之后）。内容从实战错误中提炼，只写模型真会犯的错：

1. 规划任务标准流：读上下文 → 不确定点一次性 ask_user → plan_save 落盘 → 一句话收尾。修订走 planId 更新。
2. 写作任务标准流：memory_search 校对设定 → chapter_read 读上下文 → 写入工具落库 → 简短收尾。
3. 工具调用只能走 function calling；正文中出现工具名即违规。
4. 一次任务提问预算 2 次；能合并的问题合并问。
5. 同一产物（计划/章节）在一次任务里只落盘一次，后续都是修订。
6. 遇到工具报错：读错误信息调整参数重试，最多 2 次，仍失败则如实告知作者。

### D2 写作文笔知识集（怎么写得好，按需检索）

**存储**：复用 `projectMemoryEntry` 表结构新增全局知识表（或新表 `writingKnowledge`），字段：genre（题材）、topic（主题：开篇/对话/打斗/情感/悬念钩子/节奏…）、content（≤400字守则卡）。

**内容分两层**：
- 通用文笔规范卡（题材无关，10-15 张）：视角一致性、展示优于陈述、对话推动剧情、章节钩子结构、避免形容词堆砌、场景转换节奏等。
- 题材文风卡（每题材 5-8 张）：科幻（硬设定自洽、术语密度控制）、悬疑（信息释放节奏、红鲱鱼）、玄幻（力量体系规则感）、都市（生活质感、口语化对话）、言情（情感递进层次）等。首批覆盖平台主推的 4-6 个题材。

**注入策略**：
- 常驻：通用规范卡按重要性取 top3 拼入 system prompt（≤300字）。
- 按需：根据作品 tagNames 匹配题材，写作类任务（build 模式且含 chapter_write/append）自动注入该题材文风卡 top3；其余靠新增只读工具 `writing_guide_search(topic)` 让模型自查（如写打斗前查"打斗"卡）。

**数据来源**：首批由主窗口人工撰写（每张卡 200-400 字），后续可从精品章节反向提炼。

### D3 与现有 L2 记忆的关系

作品级记忆（风格规则/角色卡）继续走 projectMemoryEntry，是"这本书怎么写"；知识集是平台级，"这类书怎么写"。注入顺序：身份 → 模式契约 → 决策策略 → **操作守则** → **文笔规范** → 作品规则包 → 故事记忆摘要。作品级规则排在知识集之后（更靠近对话，权重更高），确保作者个性化设定优先于平台通用守则。

## 七、方案 E：内置 Skill 体系（工作流模板化）

Skill = 触发条件 + 流程模板 + 输出检查清单，本质是"针对特定任务型态的增强提示词包"，不引入新的执行引擎，实现成本低、收益直接。

### E1 实现形态

- 新增 `api/lib/agent/skills/` 目录，每个 skill 一个 ts 文件导出 `{ name, trigger, prompt }`。
- trigger 为轻量意图匹配（关键词/正则 + 模式），在 `assembleContext` 组装时判定命中，命中则把该 skill 的 prompt（≤500字）作为独立 system 段注入。
- 每次最多命中 1 个 skill（按优先级），避免提示词膨胀。

### E2 首批四个内置 Skill

| Skill | 触发 | 流程模板要点 | 检查清单 |
|---|---|---|---|
| 章节规划 | plan 模式 + "规划/大纲/计划第X章" | 读前章结尾+伏笔 → 合并提问（≤1次）→ plan_save → 一句话收尾 | 是否读了上一章？计划是否含：剧情目标/场景序列/出场人物/伏笔处理/结尾钩子五要素？是否重复落盘？ |
| 章节写作 | build 模式 + "写/续写第X章" | memory_search 校对 → 读上一章结尾 → 若有对应计划先读计划 → 分段写入 → 收尾 | 视角是否一致？是否呼应计划？钩子是否落地？字数是否达标？ |
| 修订润色 | build 模式 + "改/润色/调整"+已有内容 | 读原文 → 明确修改范围 → chapter_edit_range 精准修改（禁止全文重写）→ 收尾 | 是否只动了要求的范围？是否保留了原文风格？ |
| 一致性审阅 | review 模式 | memory_search 拉全量设定 → 逐章比对 → 结构化问题清单 | 每条是否含位置/问题/建议修法三要素？ |

### E3 与知识集的配合

Skill 管"流程对不对"，知识集管"内容好不好"。章节写作 Skill 的模板里显式引用文笔知识："写作前用 writing_guide_search 查当前场景类型的写作守则"。

## 八、方案 F：交互层——计划审查条（治 P5）

复用章节审查（pendingReview ✓/✕）的完整模式，扩展到计划产物：

### F1 后端

- plan_save 的更新分支（带 planId 或同名命中）返回 display 扩展为 `planDiff`：`{ kind: 'planDiff', artifactId, title, before, after }`（新建时 before 为 null，保持现有 planFile display 不变或统一切换）。
- agent-events.ts 契约增加 planDiff display kind。

### F2 前端

- StudioWorkspace 收到 planDiff 事件 → 生成 `PlanPendingReview`（结构对齐 ChapterPendingReview：before/after/描述）→ AgentPanel 顶部复用现有绿色✓/红色✕审查条。
- 批准：保留新内容（已落库，仅清除审查态）；拒绝：调 updateNovelPlanFile 回写 before 内容（新建场景则 saved:false 软删除）。
- 计划编辑器（workspaceDocument plan 分支）在审查未决时显示"待审查"角标，与正文一致。

### F3 范围控制

- 计划审查为**非阻塞**（落库后事后审，与章节一致），不走审批信箱挂起——规划迭代频繁，阻塞式审批会把体验拖垮。

## 九、分阶段实施计划

### P0（立竿见影，治本次全部可见问题）——预计一个执行窗口

1. 方案 A：提示词信道纪律重写（A1-A3）
2. 方案 B1+B2：plan_save upsert + ask_user 预算
3. 方案 B3：计划列表同名去重
4. 方案 C1：伪调用检测扩展

验收：重跑"帮我规划第X章"任务——正文无旁白、提问≤2次、二次回答后原计划就地更新（树中无重复文件）、正文不粘贴计划全文。

### P1（护栏加固 + 计划审查）——一个执行窗口

1. 方案 C2 旁白熔断 + C3 Plan 模式落盘约束 + A4 长上下文提醒
2. 方案 F：计划审查条全链路

验收：故意诱导模型输出旁白（长上下文续跑），正文仍干净；计划修订出现✓/✕审查条，拒绝后内容回滚。

### P2（知识集 + Skill，长期质量建设）——1-2 个执行窗口

1. 方案 D1 操作知识集（随 P0 提示词一起上也可，内容独立）
2. 方案 D2 文笔知识集：先通用规范卡常驻 + 题材卡按 tagNames 注入（暂不做检索工具），效果验证后再上 writing_guide_search
3. 方案 E：四个内置 Skill（先上章节规划+章节写作两个高频 Skill）

验收：不同题材作品的写作输出在文风上有可感知差异；规划/写作任务全流程无需人工纠偏。

## 十、风险与兼容

| 风险 | 缓解 |
|---|---|
| system prompt 持续膨胀 → 每轮 token 成本上升 | 操作守则+通用文笔卡合计控制在 1000 字内；Skill 单命中；题材卡只在写作任务注入 |
| 旁白熔断误判（正常结论被改道进思考区） | 模式表只收录高置信报幕句式；只在中间轮次（finishReason=tool_calls）生效，最终轮正文永不改道 |
| plan_save 同名自动更新误伤（作者故意要两份同名计划） | output 中明确告知"已就地更新"；作者可在树里手动复制一份另存 |
| 提问预算太紧导致模型瞎猜 | 预算 2 次 + 提示词强调"合并提问"；后续可按模式差异化（plan 模式 2 次、build 模式 1 次） |
| 知识集内容质量参差 | 首批全部人工撰写评审；卡片带 importance 分级，注入时按分取 top |
| 历史重复计划数据 | B3 列表去重自动收敛，无需数据迁移 |

## 十一、本方案不做的事

- 不引入多 Agent 编排（storyPlanner 子代理等仍按 plan/13 的 P2 节奏走，本方案的 Skill 层是其轻量前置）。
- 不更换模型或调采样参数（幻觉治理优先走提示词+护栏，成本更低且可回滚）。
- 不做计划的阻塞式审批（保持事后审查，理由见 F3）。
