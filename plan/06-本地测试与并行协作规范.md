# 启创墨域本地测试与并行协作规范

## 1. 当前阶段硬约束

当前项目仍处于测试阶段，所有开发、联调、验收都只允许在 `本地服务器` 运行。

本阶段明确禁止：

- 直接部署到公网
- 提前接入公网域名
- 为上线环境改造安全策略之外的生产配置
- 以“方便预览”为由跳过本地联调

当前阶段默认目标：

- 本地开发
- 本地接口
- 本地数据库或本地模拟数据
- 本地对象存储或本地占位资源

等测试验收完成后，再单独规划公网部署、域名、环境变量、安全加固和发布流程。

---

## 2. 是否适合并行多窗口协作

可以，但不建议所有模块同时无边界并行。

原因：

- 这个项目既有前端页面，也有创作工作台、社区、聊天、后端接口、AI 封面链路
- 如果不先约定边界，很容易出现多人同时改：
  - 路由
  - 公共组件
  - 全局状态
  - 类型定义
  - API 契约
- 最终会导致互相覆盖、返工和风格失控

因此推荐方案不是“全量并行”，而是：

> 分两轮并行 + 明确文件边界 + 主窗口总控审阅

---

## 3. 推荐协作方式

## 3.1 主窗口职责

你当前主窗口只做这几件事：

- 读取 `plan` 文档
- 下发任务
- 审核各窗口产出
- 解决冲突
- 决定合并顺序

主窗口尽量不要直接写大量业务代码，否则会和其他窗口抢文件。

## 3.2 第一轮并行

第一轮只开 3 个执行窗口：

1. 基础架构与设计系统
2. 阅读与发现链路
3. 后端骨架与数据契约

这一轮的目标是先把：

- 项目骨架
- 路由结构
- 设计 token
- mock 或本地接口契约
- 阅读消费链路

先固定下来。

## 3.3 第二轮并行

等第一轮稳定后，再开 2 个执行窗口：

4. 创作中心与 AI 封面
5. 社区、聊天与个人中心

原因：

- 创作中心依赖基础布局和接口契约
- 社区和聊天依赖用户、评论、消息数据结构
- 这些都要建立在第一轮基础上

---

## 4. 冲突控制原则

### 4.1 公共文件归属

以下文件默认只允许 `基础架构窗口` 修改：

- 项目入口
- 全局路由
- 应用外壳
- 设计 token
- 全局样式
- 公共基础组件

其他窗口如果需要调整，只能：

- 提出需求
- 由总控窗口决定
- 或由基础架构窗口统一修改

### 4.2 业务模块按目录分治

推荐从一开始就按模块目录拆开：

- `discover`
- `novel`
- `reader`
- `studio`
- `community`
- `messages`
- `profile`
- `server`

做到：

- 谁负责谁的模块
- 不跨模块随意改文件

### 4.3 接口契约优先

所有业务窗口应先遵守后端契约或共享类型，不要各自发明字段名。

优先保证：

- 命名统一
- 类型统一
- 状态统一

## 6. 最终建议

当前最优协作方式是：

- 1 个主窗口总控
- 第一轮 3 个执行窗口
- 第二轮 2 个执行窗口

这比“5 个窗口同时乱写”更高效，也更容易保证最终质量。
