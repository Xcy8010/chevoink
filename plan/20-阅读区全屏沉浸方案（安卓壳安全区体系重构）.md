# 20-阅读区全屏沉浸方案（安卓壳安全区体系重构）

> 目标：APP 内阅读区达到番茄小说级的全屏沉浸——**状态栏图标与系统底栏都不显示，正文铺满整块屏幕**。
> 铁律：除阅读区外，全站任意页面（首页/发现/社区/创作区/消息/设置/作品页/平板/桌面）的顶部与底部留白**零变化**；键盘避让链路零退化。
> 前置结论：本方案基于第 19 号方案产出的 Capacitor 远程壳，`server.url` 指向线上站点，**Web 改动部署即生效**。

---

## 0. 先纠正一个此前的错误建议

在本方案之前，口头结论是「要做全屏沉浸就得移除 `styles.xml` 里三处 `windowOptOutEdgeToEdgeEnforcement`」。**这个方向是错的，本方案否决它**，理由见第 3 节。

正确路径是：**保留 optOut，只在阅读区运行时调用 `StatusBar.setOverlaysWebView(true) + hide()`**，把改动面锁死在阅读区。这样做的额外好处是它属于纯 Web 改动，不必重打 APK。

## 3. 为什么否决「移除 optOut」（反方案论证）

移除 `styles.xml` 三处 `windowOptOutEdgeToEdgeEnforcement` 会让**整个 APP** 立刻进入 edge-to-edge，后果：

1. **全站顶部塌陷**：`env(safe-area-inset-top)` 在 Android WebView 里只反映 display cutout，不等于状态栏高度；首页/社区/创作区的顶部导航会被状态栏压住，需要为上表 21 处逐一重新适配 —— 违反本方案铁律；
2. **键盘避让整体失效**：`decorFitsSystemWindows=false` 后 `adjustResize` 不再收缩窗口，`interactive-widget=resizes-content` 拿不到布局视口变化，`keyboard-inset.ts` 的三路信号（visualViewport / VirtualKeyboard / 焦点+高度回升）会同时失灵，直接打坏创作区正文编辑、章节评论、发帖、聊天四处输入；
3. **改动必须重打 APK**，每次调参都要走一遍 `assembleRelease` + 上传 + 用户重装，验证成本极高；
4. **收益为零**：目标只是阅读区一个页面全屏，代价却是全站布局体系重构。

对比之下，`StatusBar.setOverlaysWebView(true)` 是**运行时、可随时开关、作用域可控**的等价能力（其 Android 实现即是对当前 window 设 `decorFitsSystemWindows(false)`），并且 optOut 声明**不会阻碍它**——optOut 只改变系统的默认强制行为，显式 API 调用优先级更高。

> **结论**：`styles.xml` 一行不改，optOut 保留。保留它正是「非阅读页零影响」的保障。

## 5. 方案 A 落地步骤

### 5.1 第一步：扩展原生插件封装（`src/lib/native-app.ts`）

`StatusBarPlugin` 类型当前只声明了 `setBackgroundColor / setStyle / hide / show`，需补两个方法：

```ts
type StatusBarPlugin = {
  setBackgroundColor?: (options: { color: string }) => Promise<void>
  setStyle?: (options: { style: 'DARK' | 'LIGHT' | 'DEFAULT' }) => Promise<void>
  setOverlaysWebView?: (options: { overlay: boolean }) => Promise<void>
  getInfo?: () => Promise<{ visible: boolean; height?: number }>
  hide?: () => Promise<void>
  show?: () => Promise<void>
}
```

新增两个导出函数（都要 `isNativeApp()` 守卫、都要 `.catch(() => {})` 静默）：

- `enterNativeImmersive(): Promise<void>` —— 顺序严格为 ①`setOverlaysWebView({overlay:true})` → ②等一帧 → ③`hide()`。**顺序不可颠倒**：先 hide 再 overlay 会重现「窗口黑底」问题（已踩过）。
- `exitNativeImmersive(backgroundColor, dark): Promise<void>` —— 顺序为 ①`show()` → ②`setOverlaysWebView({overlay:false})` → ③`setBackgroundColor` + `setStyle` 还原主题色。

两个函数都返回 Promise，供阅读区在 await 后再触发安全区重测。

### 5.2 第二步：阅读区接入（`ReaderMobile.tsx`）

在现有的「染色 effect」位置替换为沉浸 effect：

```ts
useEffect(() => {
  let cancelled = false
  void enterNativeImmersive().then(() => {
    if (!cancelled) refreshSafeAreaTop()   // 5.3 提供
  })
  return () => {
    cancelled = true
    void exitNativeImmersive(themeAppBg, themeIsDark).then(refreshSafeAreaTop)
  }
}, [])
```

要点：

- **只在 mount/unmount 各做一次**，不要挂在 `[tone.swatch]` 上——overlay 切换会改变 WebView 尺寸，跟着 tone 反复切会引起重排抖动（A8）；
- 底色切换仍走既有的 `html`/`body`/`meta[theme-color]` 染色 effect，与 overlay 解耦；
- 卸载分支必须还原成主题色而非阅读底色，否则退出后首页顶部会残留纸色（A4）；
- `ReaderTablet` 与桌面布局**不接入**（A7）；仅 `ReaderMobile` 这一个入口。

### 5.3 第三步：安全区取值来源（`safe-area.ts` 重构，本方案技术核心）

overlay 生效后，顶部安全区的**真实值必须来自可信来源**。三个候选源按优先级：

| 优先级 | 来源 | 可信度 | 备注 |
| --- | --- | --- | --- |
| 1 | `env(safe-area-inset-top)` 探针实测 | 待验证 | Android WebView 在 overlay 下**可能**开始上报；若 > 0 直接用，最精确 |
| 2 | `StatusBar.getInfo().height` | 待验证 | 单位为 px 还是 dp 需实测（除以 `devicePixelRatio` 前后各测一次） |
| 3 | 固定兜底 `32px` | 不精确 | 现有 `ANDROID_STATUS_BAR_FALLBACK`，仅当 1、2 都拿不到时使用 |

**落地前必须先取证**（沿用本次奏效的方法，不要靠截图猜像素）：临时在阅读区渲染一行诊断文本，在 `enterNativeImmersive()` 之后打印

```
env 探针值 / getInfo().height / dpr / innerHeight / screen.height / 根容器 rect.top
```

真机截图确认后，再据实测结果决定 `safe-area.ts` 走优先级 1 还是 2，然后删除诊断条。

`safe-area.ts` 需要的改造：

1. 导出 `refreshSafeAreaTop()`，把现有 `apply()` 从闭包内提出来供外部主动调用（overlay 切换不触发 `resize` 事件时也能重测）；
2. 兜底分支的 `immersive` 判定（`innerHeight >= screen.height - 1`）在 overlay 下会成立，需确保它**只**在 `env` 与 `getInfo` 都失败时才注入 32px；
3. `--safe-bottom` 同步处理：overlay 会一并放开底部，若 `env(safe-area-inset-bottom)` 仍为 0，底部手势条会压住页码栏（A3），需用同一套优先级取值。

### 5.4 第四步：状态栏隐藏的稳定性（原生侧，已就绪）

`MainActivity.java` 已设 `setSystemBarsBehavior(BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE)`。这行代码是上一轮为 hide 方案加的，当时因未配 overlay 而空转，**在本方案中正是必需项**：没有它，翻页的每次点按都会把状态栏拽回来，且临时恢复的状态栏自带黑色蒙层、忽略一切颜色设置。

结论：原生侧**无需任何新改动**，现有 APK（versionCode 3 / 1.0.2）即可承载方案 A。

## 6. 键盘链路零影响论证（A6）

overlay 会破坏 `adjustResize`，这是方案 B 的致命伤。方案 A 规避方式：

1. **阅读区无任何输入框** —— 正文、代入页、页码栏、返回/「…」按钮全部只读；
2. 阅读区内四个 `BottomSheet`（目录 / 章节评论 / 阅读设置 / 听书设置）中，**章节评论面板含输入框**，是唯一风险点。处置：评论面板打开时先 `exitNativeImmersive()`（临时退出沉浸），关闭后再 `enterNativeImmersive()`。面板本身是遮盖全屏的浮层，切换过程用户看不到顶部变化；
3. `@capacitor/keyboard` 保持不配置、维持默认 `resize: native`，`keyboard-inset.ts` 一行不改；
4. 其余所有输入位（创作区正文、发帖、聊天、设置）都在阅读区之外，overlay 已还原，链路不变。

## 9. 方案 B 备用触发条件（未来必做，不是现在）

`targetSdkVersion` 目前是 35。**当它升到 36（Android 16）时，`windowOptOutEdgeToEdgeEnforcement` 会被系统忽略**，全站会被强制 edge-to-edge —— 届时第 3 节列举的四项后果会全部发生，且不可回避。

前置准备（升 targetSdk 之前必须先做完）：

1. 原生侧用 `ViewCompat.setOnApplyWindowInsetsListener` 取 `WindowInsetsCompat.Type.systemBars()` 的 top/bottom，除以 `density` 得 CSS px，通过 `bridge.getWebView().evaluateJavascript` 或 `bridge.triggerWindowJSEvent` 注入前端，前端写入 `--safe-top` / `--safe-bottom`（这是唯一可信的 inset 来源，`getInfo().height` 只覆盖状态栏、不覆盖挖孔与手势条）；
2. 单独对 `WindowInsetsCompat.Type.ime()` 给 WebView 设 bottom padding，恢复键盘避让（`systemBars` 不设，才能保住内容延伸）；
3. 按第 2.3 节全清单逐页核对 41 处安全区消费点；
4. 平板/桌面断言零影响后再发版。

方案 A 与方案 B 不冲突：A 已经把「阅读区依赖可信 safe-top」这条通路建好，B 到时只需替换取值来源（第 5.3 节的优先级表新增一条最高优先级「原生注入值」）。

## 10. 尚未验证的未知项（落地时必须先测，不要预设结论）

1. **overlay 模式下 `env(safe-area-inset-top)` 是否上报非 0**：决定第 5.3 节走优先级 1 还是 2。当前壳内实测为 0，但那是非 overlay 状态，不能外推；
2. **`StatusBar.getInfo().height` 的单位与精度**：需在同一台机上与状态栏实际像素高比对；
3. **overlay 切换是否产生可见闪动**：若有，用 `tone.background` 铺一层同色遮罩覆盖切换帧；
4. **`hide()` 后 `env` 是否再次归零**：hide 与 overlay 是两个独立状态，组合行为需实测；
5. **章节评论面板临时退出沉浸的视觉连续性**：若出现顶部闪现，改为「评论面板打开时不退出沉浸，改用 `@capacitor/keyboard` 的 `keyboardWillShow` 事件手动写 `--keyboard-inset`」。

> 取证方式统一为「页内诊断文本 + 真机截图」，一轮取全所有数值再动手改。本次修复过程中，靠截图像素反推连续四轮误判，页内诊断一次定死根因——这条经验对本方案同样适用。

## 12. 落地实录（2026-07，与上文预设不符处以本节为准）

第 10 节的取证按要求执行了（页内诊断条 + 真机截图），**未知项 1 的答案是否定的，方案 A「原生侧零改动」的前提被实测推翻**：

- 实测数据：`envT=0 envB=0 info=h/0 ih=748 sh=802` —— `StatusBar.setOverlaysWebView(true)` 静默失败（`ih` 未扩张到 802），只有 `hide()` 生效，状态栏区域露出窗口黑底；
- 根因（读 `@capacitor/status-bar@8.0.3` 安卓源码确认）：`setOverlaysWebView` 的实现基于 `SYSTEM_UI_FLAG_LAYOUT_FULLSCREEN` 这套 **legacy systemUiVisibility flag，Android 15（targetSdk 35）起被系统忽略**；第 5.1 节「optOut 不阻碍 setOverlaysWebView」的推断只对 Android 14 及以下成立。

实际落地形态（替代第 5.1/5.4 节）：

1. **自定义原生插件** `ImmersiveModePlugin.java`（chevoink-android，注册于 `MainActivity.onCreate` 的 `super` 之前）：
   - `enter()`：先读 `systemBars|displayCutout` insets（隐藏后归零，必须先读）换算 CSS px 返回给网页 → 设 `LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES`（防挖孔行黑条）→ `setDecorFitsSystemWindows(false)`（现代 API，不受 legacy flag 废弃影响，显式调用优先级高于主题 optOut）→ `hide(systemBars())`；
   - `exit()`：`show(systemBars())` → `setDecorFitsSystemWindows(true)` → cutout 模式还原 DEFAULT；
2. **Web 侧能力检测**：`supportsNativeImmersive()` 检测 `Capacitor.Plugins.ImmersiveMode.enter`，旧 APK（≤1.0.2）检测不到 → 完全不进沉浸，保持既有「状态栏染色」形态，零布局改动（这就是止血策略，无需强更）；
3. **安全区取值**：`enter()` 返回的 insets（CSS px）直接注入 `--safe-top/--safe-bottom`，`safe-area.ts` 的三级优先级保留为兜底（env → 原生 insets → 32px/24px）；
4. **发版**：1.0.3 / versionCode 4，三处版本号已同步，APK 与 version.json 已上线。

第 5.2（ReaderMobile 接入）、第 5.3（safe-area 三级取值）、第 6 节（评论面板临时退出沉浸）按原方案落地，未变。
