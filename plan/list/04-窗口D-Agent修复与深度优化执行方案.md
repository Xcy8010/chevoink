# 窗口 D：Agent 修复与深度优化执行方案

## 1. 目标

本方案不再围绕“继续补几个关键词”做零碎修补，而是把当前 Agent 的问题拆成：

1. **先恢复可用性**：确保“让 Agent 写第一章”这类核心链路稳定闭环。
2. **再恢复 Agent 性**：让 Agent 能基于项目状态、工具能力、接口契约和当前工作区上下文，自主规划并执行，而不是依赖前端穷举式提示词判断。
3. **最后做长期架构**：把 Agent 从“会输出内容的聊天框”升级为“真正能读状态、做决策、调工具、同步工作台”的执行中枢。

---

## 2. 当前现状判断

结合当前代码与线上现象，问题不是单点 bug，而是整条链路存在职责分裂：

1. **任务识别过于前端化**
   - 当前大量依赖 `StudioWorkspace.tsx` 中的关键词判断与 fallback。
   - 这会让 Agent 行为更像“输入分类器”，而不是“结合工作区状态做决策的执行体”。

2. **规划与执行没有完全闭环**
   - 当前已经有 `actionPlan`、`toolPolicy`、`executionMode`，但仍有不少执行依赖前端再判断一次。
   - 导致“思考里决定了新建章节”，最终却不一定真的创建章节。

3. **前端仍在承担过多业务决策**
   - 当前前端不仅负责 UI，还负责：
     - 推断任务
     - 解释 action plan
     - 自动写回章节
     - 根据当前选中状态决定目标章节
   - 这会让“选中了计划文档”“选中了目录”“当前没有章节”“当前有本地草稿”等状态互相污染。

4. **章节写作缺少强制分步执行机制**
   - 现在的“新建章节 + 标题 + 正文”更像一次性内容回填。
   - 但你需要的是标准 Agent 行为：**先创建实体，再命名，再写正文，再同步 UI**。

5. **Prompt 设计偏局部规则补丁**
   - 目前已经补了不少规则，但仍然偏“防错提示词”。
   - 你要的是让 Agent 理解：
     - 当前项目有哪些工具
     - 各工具的权限与适用时机
     - 什么叫全局工作区视角
     - 什么场景必须先建实体再写内容

---

## 3. 核心设计原则

后续修复与优化统一遵守下面 6 条原则：

1. **后端主控，前端只做呈现与局部确认**
   - Agent 的规划、执行决策、工具选择，统一以后端为主。
   - 前端不再承担“第二次猜测 Agent 意图”的核心职责。

2. **工具优先，不靠正文猜结果**
   - 需要改工作台状态的任务，必须优先走工具链。
   - 不能再出现“正文已经生成，但章节实体没创建”的半完成状态。

3. **分步执行，步骤可见**
   - 类似“写第一章”必须拆成：
     1. 创建空白章节
     2. 命名章节
     3. 写入正文
     4. 同步章节树与编辑区
   - 每一步都要有明确成功/失败状态。

4. **全局工作区视角**
   - Agent 的行为不能被“当前正打开的是计划文档/目录文档”误导。
   - 当前选中内容只作为参考，不得成为唯一目标。

5. **项目深度绑定**
   - 内置提示词必须明确：
     - 项目目标
     - 工作区数据结构
     - 可用工具与策略
     - 不同任务的标准执行范式

6. **可观测、可追踪、可验收**
   - 不能只看聊天输出。
   - 必须能看到：计划、执行步骤、每步结果、最终工作台状态。

---

## 4. 目标架构

### 4.1 总体结构

将 Agent 统一重构为三层：

1. **Intent Layer（意图理解层）**
   - 输入：用户请求 + 当前作品状态 + 工作区上下文
   - 输出：当前任务类型、是否需要全局操作、是否需要多步执行

2. **Planning Layer（规划层）**
   - 输出标准化 `actionPlan`
   - 每一步明确：
     - `toolName`
     - `target`
     - `payload`
     - `success condition`
     - `failure strategy`

3. **Execution Layer（执行层）**
   - 严格按步骤顺序执行
   - 每一步成功后再进入下一步
   - 某一步失败时停止，并向前端返回明确失败原因

### 4.2 前后端职责重划

**后端负责：**

- 组装全局上下文
- 判断任务类型
- 决定是否需要全局操作
- 规划工具步骤
- 执行或主导执行工具步骤
- 返回结构化执行结果

**前端负责：**

- 呈现工作区状态
- 呈现步骤进度
- 响应少数需要用户确认的动作
- 同步最终结果到本地界面

---

## 5. 第一阶段：止血修复方案

目标：先把“让 Agent 写第一章，但章节树不新增”的核心问题彻底修好。

### 5.1 章节写作统一改为强制分步执行

针对以下场景：

- “给我写第一章”
- “帮我写首章”
- “写第二章”
- “写这一章”
- “续写这一章”

统一执行规范：

1. 若目标章节不存在：
   - 第一步必须执行 `chapter.create`
   - 先创建空章节实体
2. 若章节标题为空或明显占位：
   - 第二步执行 `chapter.rename`
3. 再执行 `chapter.write` 或 `chapter.append`
4. 最后刷新章节树、当前编辑区、统计信息

### 5.2 新增章节写作的强约束

对“新建章节写作”增加后端内置约束：

- 若 `actionPlan` 包含 `chapter.create`，则不允许只返回正文文本而不返回结构化执行步骤
- 若本轮目标是“新章写作”，则章节树未新增时，本轮不得标记为执行完成
- 若 `chapter.create` 失败，则后续 `chapter.rename` / `chapter.write` 不得继续执行

### 5.3 去掉当前选中文档对 Agent 目标的硬绑定

当前选中状态的优先级调整为：

1. 用户 prompt 中明确点名的章节
2. 当前已选中的真实章节
3. 最近一次有效章节上下文
4. 无章节目标时进入“创建新章节”路径

明确禁止：

- 因为当前选中的是计划文档，就把 Agent 锁死在计划文档上下文
- 因为当前没有章节实体，就直接把正文输出到聊天区当成完成

### 5.4 补齐失败反馈

当前必须补上这些失败可见性：

- `chapter.create` 失败
- `chapter.rename` 失败
- `chapter.write` 失败
- 章节树刷新失败
- 本地缓存同步失败

要求：

- 失败信息必须出现在处理状态中
- 不允许只看到正文输出，看不到失败原因

---

## 6. 第二阶段：执行链重构方案

目标：把 Agent 从“会输出 action plan 的聊天系统”升级为“会真正执行步骤的工作台代理”。

### 6.1 引入统一执行器

新增统一执行器概念：

- `WorkspaceAgentExecutor`

职责：

1. 接收标准化 `actionPlan`
2. 逐步执行工具
3. 输出 `stepResults`
4. 管理中断、失败、回滚与最终结果

每个步骤统一返回：

- `status`: `pending | running | success | failed | skipped`
- `toolName`
- `target`
- `resultSummary`
- `errorMessage`

### 6.2 让 `actionPlan` 成为唯一执行依据

当前问题之一是：

- 规划一套
- 前端再猜一套

后续统一为：

- 一旦后端给出 `actionPlan`
- 前端不得再根据正文和关键词自行重推业务动作
- 所有写工作台的操作，以 `actionPlan` 为唯一依据

### 6.3 章节写作模板化

后端内置标准执行模板：

#### 模板 A：新章起草

1. `chapter.create`
2. `chapter.rename`
3. `chapter.write`

#### 模板 B：当前章续写

1. `chapter.append`

#### 模板 C：当前章重写

1. `chapter.write`

#### 模板 D：章节命名

1. `chapter.rename`

Agent 不再靠零散推断，而是先判断属于哪个模板，再结合上下文细化参数。

### 6.4 引入步骤级回写

当前要避免“一股脑全部输出”。

改为：

1. 完成 `chapter.create` 后，章节树立即出现新章节
2. 完成 `chapter.rename` 后，章节标题立即更新
3. 完成 `chapter.write` 后，正文再进入编辑区

也就是说，UI 不再只在最后一刻统一结算，而是逐步同步。

## 7. 第三阶段：Agent 深度优化方案

目标：让 Agent 真正具备项目协同能力，而不是提示词拼接能力。

### 7.1 重写内置系统提示词

系统提示词不再只描述“你是写作助手”，而要明确以下内容：

1. **你的身份**
   - 你是创作工作台 Agent
   - 你的职责是规划、执行、同步工作区，不只是生成文本

2. **你的资源**
   - 当前作品
   - 章节树
   - 计划文件
   - 当前编辑区
   - 工具注册表
   - 工具权限策略

3. **你的执行原则**
   - 先建实体，再写内容
   - 优先用工具，不靠正文代替操作
   - 当前选中内容只是上下文，不是唯一目标
   - 若用户需求涉及多个动作，必须拆步执行

4. **你的成功标准**
   - 不仅要“回答正确”
   - 更要“工作台状态正确”

### 7.2 引入项目工作区语义包

新增一份面向 Agent 的项目语义上下文：

- 什么是作品
- 什么是章节
- 什么是计划文件
- 什么是目录文档
- 哪些操作会修改工作台状态
- 各工具适用场景

这份语义包要作为系统上下文长期注入，而不是 scattered 在多个小规则里。

### 7.3 引入 Agent 决策优先级

统一决策顺序：

1. 先判断用户目标
2. 再读取工作区当前状态
3. 再选模板
4. 再决定工具步骤
5. 最后才组织输出内容

明确禁止：

- 先写正文，再想有没有工具要调
- 因为当前界面选中了某个文档，就无脑把它当唯一目标

### 7.4 加强多动作编排能力

例如：

- “给这本书命名并补简介”
- “先写第一章，再帮我起一个章节名”
- “生成封面提示词并直接出图”

统一要求：

- Agent 必须拆成多步
- 每一步都能映射到工具
- 每一步都有结果反馈

---

## 8. 第四阶段：可观测性与调试体系

目标：防止之后再出现“思考是对的，执行是假的”。

### 8.1 必须补齐的运行状态

前端展示层至少要能看到：

1. 当前识别出的任务
2. 当前规划出的步骤
3. 当前执行到第几步
4. 每一步成功还是失败
5. 为什么跳过某一步

### 8.2 必须补齐的日志点

关键日志点：

1. 请求发起前的工作区上下文快照
2. 后端生成的最终 `actionPlan`
3. 工具权限判定
4. 每一步工具调用的输入与结果
5. 章节树同步结果
6. 自动回写成功/失败原因

### 8.3 验收时必须看结构化结果

以后验收 Agent 不能只看：

- 聊天输出得像不像

必须同时看：

- `actionPlan`
- `stepResults`
- 章节树是否变化
- 编辑区是否同步
- 失败是否可见

## 10. 分阶段实施顺序

### Phase 1：止血

目标：修复“思考新建章节，但章节树为空”。

- 新章写作强制三步执行
- 当前选中文档不再绑死 Agent 目标
- 失败可见

### Phase 2：执行链重构

目标：让 `actionPlan` 成为唯一执行依据。

- 建立统一执行器
- 建立步骤级结果结构
- 做步骤级回写

### Phase 3：Prompt 与 Agent 能力重做

目标：让 Agent 真正会利用项目上下文、工具和策略。

- 重写系统提示词
- 建立工作区语义包
- 建立任务模板

### Phase 4：观测与验收体系

目标：防止回归。

- 完善步骤展示
- 完善结构化日志
- 固化验收清单

---

## 11. 验收标准

以下全部通过，才算 Agent 恢复到可用状态：

1. 当前选中计划文档时，说“给我写第一章，字数多一点”
   - 章节树立即出现新章节
   - 章节标题随后更新
   - 正文写入该章节

2. 当前选中已有章节时，说“续写这一章”
   - 不新建章节
   - 正文追加到当前章节

3. 当前没有章节时，说“先帮我写第一章，再给这一章起个名字”
   - Agent 能拆成至少两步以上
   - 每一步都能在状态里看见

4. 当前选中计划文档时，说“给小说命名并补简介”
   - 不影响计划文档本身
   - 正确更新作品元信息

5. 任一步骤失败时
   - 用户能看到失败发生在哪一步
   - 不再出现“看起来成功，实际没落库”的假完成

---

## 12. 推荐执行方式

建议不要再继续零散补丁式推进，而是按下面顺序做：

1. 先完成 **Phase 1 止血**
2. 接着立刻进入 **Phase 2 执行链重构**
3. 再统一重写 **Prompt + 工作区语义包**
4. 最后把运行时观测补齐

也就是说，后续应从“修一个提示词”切换为“重建 Agent 的执行闭环”。

这是当前项目里最值得优先收敛的一条主链。
